1. 한 장 요약 — 무엇이 어떻게 도는가

매주 월요일 새벽, 사람이 아무것도 하지 않아도 지난주 보고서가 만들어져 공유 폴더에 쌓인다. 일곱 단계가 한 번에 돈다.

① 적재 Supabase → BigQuery raw (증분) 기존 스크립트
↓
② 적재 대조 행 수 비교 — 증분은 조용히 틀린다 기존
↓
③ 품질 검증 최근 9일치 필수값·시각 (위반이면 여기서 멈춘다) 기존
↓
④ 마트 빌드 bigquery/build.py --layer mart — 8개 표를 다시 굽는다 기존
↓
⑤ 숫자 수집 mart → JSON 하나 · SQL 9개 · 스캔 0.17 GiB 신규
↓
⑥ PDF 렌더 JSON → HTML → 3쪽 PDF (Playwright/크로미움) 신규
↓
⑦ Drive 업로드 공유 폴더에 적재 · 같은 이름이면 새 버전 신규

앞의 넷은 이미 있던 것이고, 새로 만든 것은 뒤의 셋이다. 파이프라인을 새로 짜지 않았다. 이미 도는 파이프라인의 끝에 소비자를 하나 붙였을 뿐이다.

왜 ①~④까지 CI 가 다시 도는가

보고서만 CI 로 옮기면 마트가 며칠 전 것이어도 그림은 최신처럼 나온다. 대시보드는 숫자가 틀려도 예쁘게 나온다. Supabase 도 BigQuery 도 클라우드라 러너에서 그대로 닿으므로, 같은 실행 안에서 적재부터 끝낸다.

2. 출발점 — 샘플과 실측 사이의 간극

주어진 것은 합성 데이터로 만든 샘플 PDF 3쪽이었다. WAU 1,520명 · 매출 128만원 · 5×5 코호트 표. 먼저 실유저 마트를 재봤다.

여기서 갈림길이 생긴다. 샘플 레이아웃을 실유저에 그대로 씌우면 칸의 절반이 "1/2 을 50.0%로 적은 숫자"가 된다. 레이아웃을 줄이는 대신 표기 규칙을 넣기로 했다(5장). 유저가 늘면 같은 코드가 저절로 샘플 모양이 된다.

착수 시점에 발견한 것

작업을 시작할 때 Docker 가 꺼져 있었고 raw 워터마크가 5일 밀려 있었다. 로컬 Airflow 로 주간 발송을 걸었다면 그 주는 보고서가 안 나오거나 5일 전 숫자로 나왔을 것이다. 이 관찰이 6장의 결정을 만들었다.

3. 스테이징·마트는 무엇이 바뀌었나

결론: 한 줄도 바뀌지 않았다

bigquery/staging/*.sql 10개, bigquery/mart/*.sql 8개 — 변경 0건. 새 마트를 굽지도, 컬럼을 더하지도 않았다. 보고서는 기존 마트를 읽기만 한다.

3.1 무엇을 읽었나

스테이징은 직접 읽지 않는다. 보고서가 닿는 층은 마트뿐이다. 이유는 비용이다 — stg 는 뷰라서 조회할 때마다 raw 를 다시 읽고, raw 에는 1억 2천만 행이 있다. 루커에 mart 만 연결한 것과 같은 규칙을 보고서에도 적용했다.

3.2 왜 안 바꿔도 됐나 — 주간 규칙 넷이 미리 낸 값

마트를 설계할 때 정한 네 규칙이 그대로 배당금이 됐다. 주간 보고서는 정확히 그 규칙이 상정한 소비자였다.

규칙내용주간 보고서에서 실제로 한 일
①모든 마트에 날짜 축을 둔다 어느 표든 metric_date BETWEEN 월 AND 일 로 잘라 주간이 나왔다
②비율을 굽지 않는다. 분자·분모를 싣는다 이것 덕분에 억제 규칙이 가능했다. 마트가 "32.4%"만 갖고 있었다면 분모가 2명인지 2,000명인지 알 수 없어 판단 자체를 못 한다
③distinct 를 사전 집계하지 않는다 주간 WAU·투표자·결제자를 유저×일 원자 행에서 그때그때 셌다
④퍼널·분포는 사건일/코호트일로 자른다 "그 주에 가입한 사람" · "그 주에 받은 투표"가 중복 없이 나왔다

②가 없었다면 이 보고서는 다른 물건이 됐다

억제 규칙(5장)의 전제는 분모를 알 수 있다는 것이다. 마트가 비율을 미리 구웠다면 "2학년 0.0%"를 그대로 인쇄하는 것 말고는 선택지가 없었다. 설계 결정이 반년 뒤의 선택지를 정한다는 사례다.

3.3 드러난 빈틈 둘 — 마트를 고치지 않고 메웠다

빈틈 1 · mart_user 에 첫 결제일이 없다

샘플의 "첫 결제 사용자 19명"을 내려면 유저별 최초 결제일이 필요한데 mart_user 에는 purchase_count(누계)만 있다. 마트에 컬럼을 더하는 대신 쿼리에서 계산했다 — mart_user_activity 에서 MIN(metric_date) WHERE purchase_count > 0.

왜 마트를 안 고쳤나. 컬럼 하나를 위해 8개 표를 다시 굽고 루커 5쪽의 스키마를 흔들 이유가 없다. 결제자가 0명인 지금은 계산 비용도 0이다. 결제가 실제로 생기고 이 계산이 매주 무거워지면 그때 마트로 올린다(3.4).

빈틈 2 · mart_backlog_weekly 가 8주를 못 채운다

적체 그래프는 8주가 필요한데 이 마트는 첫 신고~마지막 신고 사이의 주만 행을 만든다. 실유저는 신고가 3건뿐이라 8주 창에 한 주만 들어왔다 — 선 그래프가 끊긴다.

그래서 mart_report(신고 1건 = 1행)에서 주말 기준으로 복원했다. 정의는 그 마트와 같다 — 접수됐고(reported_at < 주말) 아직 안 봤다 (reviewed_at IS NULL OR reviewed_at >= 주말). 신고가 한 건도 없는 주도 0으로 정확히 나온다.

이것이 마트의 결함인가?

아니다. mart_backlog_weekly 는 루커 대시보드를 위해 만든 표이고, 거기서는 신고가 있는 구간만 보면 된다. 보고서는 "지난 8주"라는 고정 창을 요구하는 다른 소비자였을 뿐이다. 소비자가 늘면 같은 표에 다른 요구가 온다는 것이 기록할 값이다.

3.4 앞으로 마트를 바꿔야 할 때

  • 결제가 실제로 발생하면 — mart_user 에 first_purchase_at 을 더하는 편이 낫다. 코호트별 결제 전환을 볼 때 매번 전수 스캔하게 된다.
  • 유저가 수백 명을 넘으면 — 지금은 mart_user_activity 전수를 훑어도 싸지만(0.17 GiB), 커지면 주간 집계 마트를 하나 굽는 편이 싸진다.
  • 신고 처리 화면이 생기면 — sanction 이 채워지기 시작하므로 적체 정의에 "처리 결과"를 더해야 한다.

안전장치 — 실행 전에 스캔량을 먼저 잰다

collect.py 는 9개 쿼리를 전부 dry-run 으로 먼저 재고, 합이 상한 (5 GiB)을 넘으면 한 줄도 실행하지 않고 멈춘다. 절반 실행하고 상한에 걸리는 것이 제일 나쁘다 — 돈은 나갔는데 결과는 없다. 실측은 0.17 GiB다.

왜 Playwright 인가

기존 리포트 PDF 는 사람이 로컬 크롬으로 뽑았다. 자동 발송은 컨테이너 안에서 돌아야 하고 거기엔 크롬이 없다. Playwright 는 크로미움을 번들로 들고 온다. WeasyPrint 는 이 보고서의 카드 grid 레이아웃을 못 그려서 기각했다.

5. 억제 규칙 — 작은 표본에서 거짓말하지 않기

이 작업에서 가장 중요한 설계 판단이다. 모든 비율은 분모를 보고 표기를 바꾼다.

분모표기실제 출력 예
0관측 없음ARPPU (결제자 0명)
1~9실수 그대로2학년 0/2 · 3학년 0/3
10 이상비율참여율 9.5% (분모 21명)

전주 대비 %p 비교도 양쪽이 다 10 이상일 때만 계산한다. 임계값은 render.py 의 MIN_DEN 하나가 정한다.

왜. 2명 중 1명을 "50.0%"로 적으면 그것은 한 사람이 마음을 바꾸면 0%나 100%가 되는 값이다. 읽는 사람은 소수점 한 자리를 보고 추세를 판단하는데, 그 판단의 근거가 없다.

같은 원칙의 확장 셋

  • 분모가 없던 주는 0%로 찍지 않고 선을 끊는다. 0%로 그리면 "그 주엔 아무도 투표하지 않았다"는 없던 사실이 생긴다. 서비스가 시작되기 전 주가 그렇다.
  • 관찰 기간이 안 지난 코호트 칸은 -로 둔다. 0%로 채우지 않는다.
  • 값이 하나뿐인 차원 축은 그리지 않는다. 실유저는 전원 고등학교라 "고등학교 100%" 막대가 나올 뻔했다 — 정보가 0인 그림이다. 대신 각주로 밝힌다.

유저가 늘면 저절로 풀린다

합성 데이터(2만 명)로 같은 코드를 돌려보면 모든 칸이 비율로 나온다 — WAU 13,581명 · 매출 ₩1.58M · W2 리텐션 41.3%. 레이아웃을 두 벌 만들지 않았다.

6. GitHub Actions — 왜 여기서 돌리나

이 프로젝트의 오케스트레이터는 로컬 Docker Airflow 다. 그런데 주간 보고서만 CI 로 뺐다. 요구가 "손대지 않아도 계속 유지되는 발송" 이었기 때문이다.

선택지기각 이유
로컬 Airflow DAGPC·Docker 의존. 착수 시점에 실제로 꺼져 있었고 raw 가 5일 밀려 있었다
Windows 작업 스케줄러같은 PC 의존 + 실패가 눈에 안 띈다
Cloud Composer월 40만원대. 프로젝트 초기에 이미 기각된 선택지
Cloud Run Jobs + Scheduler무료 한도 안이지만 배포 파이프라인이 하나 더 생긴다
양쪽에서 다 돌리기마트를 동시에 구우면 서로 덮는다. 굽는 곳은 하나여야 한다

워크플로 구성

# .github/workflows/weekly-report.yml
on:
  schedule:
    - cron: "30 20 * * 0"    # 일 20:30 UTC = 월 05:30 KST
  workflow_dispatch:          # 손으로도 돌린다
    inputs: week / source / skip_pipeline

concurrency: weekly-report    # 두 번 겹쳐 돌지 않게
timeout-minutes: 45
요소값왜
비밀 3개SUPABASE_DB_URL · GCP_SA_KEY · GDRIVE_TOKEN_JSON 저장소가 프라이빗이라는 전제 위에 있다
수동 입력week · source · skip_pipeline 특정 주 재생성 · 합성으로 미리보기 · 마트 최신일 때 빠른 경로
글꼴 설치fonts-noto-cjk 없으면 PDF 가 통째로 두부(□)가 된다. 우분투 러너엔 한글 글꼴이 없다
산출물 보관upload-artifact · 90일 · if: always() 업로드가 실패한 주의 PDF 도 손으로 건질 수 있게
실패 알림GitHub 기본 메일 별도 알림 장치를 만들지 않은 이유

알아둘 것 둘

① 저장소가 60일간 조용하면 GitHub 이 스케줄을 끈다. 끄기 전에 메일이 오고, Actions 탭에서 다시 켜면 된다.

② 로컬 DAG 은 그대로 두었다. PC 가 켜진 날은 매일 돌아 대시보드가 더 자주 갱신된다. 마트는 CREATE OR REPLACE 라 두 곳에서 구워도 결과가 같다.

7. Google Drive 배송 — 서비스 계정으로는 안 된다

먼저 막힌 길

이미 있는 credentials.json(BigQuery 서비스 계정)으로 올리려 하면 반드시 실패한다. 서비스 계정은 개인 드라이브 저장 할당량이 없어서, 폴더를 공유해 줘도 storageQuotaExceeded 로 떨어진다 — 파일 소유자가 서비스 계정이 되는데 그 계정엔 담을 공간이 없다. 공유 드라이브(Workspace)가 있으면 되지만 개인 Gmail 에는 없다.

그래서 본인 계정 OAuth 리프레시 토큰을 쓴다. 발급은 한 번뿐이고 (gdrive_auth.py), 그 뒤로는 사람 없이 갱신된다.

항목선택이유
권한 범위drive.file 하나 이 앱이 만든 파일만 보고 고친다. 드라이브의 나머지는 읽지도 못한다. 구글 심사 대상도 아니다
토큰 위치로컬은 파일 / CI 는 환경변수 같은 코드가 두 곳에서 돈다. 갱신된 토큰은 로컬에서만 파일에 되쓴다
같은 이름일 때파일을 늘리지 않고 새 버전 링크가 유지돼야 "지난주 보고서"를 가리킨 메모가 안 깨진다
폴더 권한파일이 폴더에서 상속 폴더를 한 번 공유해 두면 이후 모든 보고서가 같은 공개 범위를 따른다

지금의 한계

  • 실유저 표본이 작다. 보고서 칸의 상당수가 실수 표기다. 이것은 보고서의 결함이 아니라 실측의 정직한 반영이다.
  • 매출 지표가 전부 0이다. MVP 충전이 스텁이라 구조상 그렇다. 3쪽은 당분간 하트 흐름이 주인공이다.
  • 신고 적체는 계속 늘기만 한다. 처리 화면(sanction)이 없어서다. 매주 1쪽 오른쪽 끝에서 이 숫자가 보인다 — 착수 시 3건, 이틀 뒤 8건.
  • PC 가 꺼져 있어도 보고서는 나오지만, 로컬 Airflow 의 일일 마트 갱신은 멈춘다. 대시보드 신선도는 여전히 PC 에 달려 있다.

다음에 손댈 만한 것

  1. 신고 처리 화면 — 보고서가 매주 가리키고 있는 유일한 운영 부채
  2. 결제가 생기면 mart_user.first_purchase_at 승격 (3.4)
  3. P3 NEIS DAG 화 — 이 프로젝트에 남은 마지막 미완 항목

한 줄로

파이프라인을 새로 만들지 않고, 이미 도는 파이프라인의 끝에 소비자를 하나 붙였다. 마트가 규칙을 지켜 구워져 있었기 때문에 stg·mart 를 한 줄도 고치지 않고 끝났고, 실행 위치만 PC 밖으로 옮겨 "손대지 않아도 유지"를 만들었다.
