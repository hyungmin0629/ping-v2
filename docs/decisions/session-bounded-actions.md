# 유저의 직접 행동은 접속 세션 안에서만 일어난다 — v5

**결정** — 투표·힌트·글·댓글·좋아요·신고·차단·공지열람을 **접속 세션 창 안**에서만
만든다. 30분 넘게 비면 새 세션으로 나눈다. 자리가 없으면 **그 행동을 만들지 않는다.**

**이유** — v4 는 `user_session` 과 `vote_session` 을 **따로** 만들었다. 서로의 시각을
몰라서 투표 세션의 **3.84%** 만 접속 세션 창 안에 있었고, 접속 1회당 투표 세션 비가
**1.01 → 6.45** 로 드리프트했다. "앱 열기 → 투표 시작" 퍼널이 통째로 불가능했다.

30분 규칙은 실서비스 `touch_session()`(`db/rls/session_log.sql`)과 **같은 정의**다.
정의가 갈리면 합성으로 짠 대시보드가 실데이터에서 다르게 나온다.

**대안** — 접속 세션을 먼저 만들고 투표를 그 안에 배치하는 안을 기각했다.
투표 물량은 `sessions_per_month_by_tier`(잔존 구간별 활동 강도)가 정하는데,
접속 세션이 먼저면 그 설계가 접속 세션 수에 종속된다.
**투표에서 접속 세션을 유도하는** 쪽이 기존 설계를 지킨다.

## ⚠️ 하루 상한은 개수가 아니라 시간이다

처음엔 하루 **12세션**으로 잘랐다. 결과는 이랬다 —

| | 개수 상한(12회) | 시간 예산(6시간) |
|---|---|---|
| 총 행 | 9,509만 | **1억 2,370만** |
| 상위 10% 지목 점유 | 39.0% ❌ | **49.8%** ✅ |
| 하루 투표 시간 최대 | — | 7.9시간 |

**헤비유저가 통째로 사라져 분포를 죽였다.** 막아야 하는 것은 "많이 한다"가 아니라
**하루에 낼 수 없는 시간을 쓴다**는 것뿐이었다(v4 최대 406.8시간/일).
그래서 시간 예산만 걸고 그 안에서는 내버려 둔다. 상한은 개수가 아니라 **시간에서 유도된다.**

**⚠️ 하루 상한이 투표를 품은 창을 자르면 안 된다.** 자르는 순간 그 투표 세션이
접속 세션 밖으로 나간다. 첫 구현에서 포함률이 95%에 그친 원인이었다.

## 영향

- 투표 세션이 접속 세션 안에: **3.84% → 99.99%**
- 접속 1회당 투표 세션: 1.01~6.45 드리프트 → **1.21~1.85**
- **복귀를 `user_session` 으로도 잴 수 있다** — v4 는 0명이었다(최대 공백 11일 20시간).
  v5 는 748명이고 `vote_session` 으로 재도 같다
- 신고 −63% · 댓글좋아요 −79% · 공지열람 −44% — 활동이 끝난 유저의 행동이 사라졌다.
  **동작은 맞다.** v4 수준 볼륨을 원하면 설정 비율을 올려야 한다
- ⚠️ **시간대 대비가 5.3배 → 3.1배로 약해졌다.** 30분 안에 이어지는 행동이 한 세션으로
  묶이면서 저녁 봉우리가 낮아진다. 더 현실적인 모양이지만 히트맵 색 대비는 줄었다 —
  시간대 분석은 세션 수가 아니라 `vote_item.served_at` 으로 세는 편이 낫다
