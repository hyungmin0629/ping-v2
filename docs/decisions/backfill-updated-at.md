# 대량 적재 후 `updated_at` 을 각 행의 원래 시각으로 되돌린다

**결정** — `db/ddl/96_backfill_updated_at.sql` 을 95(시퀀스 재동기화)와 같은 자리에
두고, 대량 적재 직후 함께 돌린다.

**이유** — `updated_at` 의 기본값은 `now()` 다. COPY 로 786만 행을 부어 넣으면
그 786만 행이 전부 "적재한 순간"이 된다. 3개월치 데이터가 하루에 뭉친다.

BigQuery raw 테이블은 `updated_at` 으로 파티션을 나눈다. 전부 한 파티션에 들어가면
파티션 가지치기가 통째로 무력해지고 쿼리마다 786만 행을 다 읽는다. 무료 등급
(월 1TB)에서 이건 실제로 아픈 비용이다.

**대안** — 파티션 기준을 `created_at` 으로 잡는다. 기각. `created_at` 이 없는
테이블이 있고(`vote_candidate`), 그러면 파티션 컬럼이 테이블마다 달라져
004 로 통일한 것이 도로 흩어진다.

**영향**
- 되돌릴 때 트리거를 껐다 켠다. 켜둔 채 UPDATE 하면 트리거가 방금 넣은 값을 다시
  `now()` 로 덮어써서, 아무 일도 하지 않은 것처럼 끝난다.
- `vote_candidate`(379만 행)와 `meal_menu_item` 은 자기 시각이 없어 부모의 시각을
  물려받는다. 후보는 출제와 동시에 만들어지므로 `vote_item.served_at` 이 실제 생성 시각이다.
- 원래부터 `updated_at` 이 있던 4개 테이블(`app_user`·`school`·`post`·`post_comment`)은
  건드리지 않는다. 그 값은 **진짜 수정 이력**이라 `created_at` 으로 덮으면 데이터를 잃는다.
