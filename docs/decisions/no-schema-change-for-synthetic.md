# 합성 데이터를 위해 스키마를 바꾸지 않는다

**결정** — 40표 342컬럼 안에서만 합성 데이터를 만든다. 팀원 체크리스트가 요구한
**A/B 실험 4표**(`experiment`·`assignment`·`exposure`·`event_log`)와
**통합 이벤트 로그**를 추가하지 않는다.

**이유** — 스키마 변경은 로컬만의 일이 아니다. `db/ddl/` 과 `db/migrations/` 는
**로컬과 Supabase 가 공유**하므로 "합성 데이터 전용 스키마 변경"은 성립하지 않는다
([[TEAM-PLAN]] 1장). 분포의 비현실성은 거의 전부 파라미터 문제였고, 실제로
파라미터만으로 40표를 다 채웠다.

**대안 — 무엇을 포기했나**

| 포기한 것 | 대신 |
|---|---|
| A/B 실험 배정·노출 기록 | **자연 실험.** 학교를 순차로 여니 "9월 개통 vs 3월 개통" 이라는 시차 도입 구조가 저절로 생긴다. 무작위 배정이 아니라 인과 주장은 약하다 |
| 통합 `event_log` | 정규화 테이블 위에서 표현 가능한 결함 4종만 — 지연 적재 · 세션 종료 누락 · 중복 · QA 계정 |
| 타입 불일치·빈 문자열 오염 | **Postgres 제약이 애초에 막는다.** 넣으려면 제약을 풀어야 하고, 그건 P0 에서 16종 위반을 차단하려고 만든 구조를 되돌리는 일이다 |
| 힌트 구매 실패 기록 | 남길 곳이 없다. [[heart-economy-rebalance]] 참조 |

**⚠️ DW 에서 잡아야 할 문제와 DB 가 애초에 막는 문제는 다르다.** 이 구분 자체가
이 프로젝트에서 배울 것 중 하나다.

**영향** — 실험 테이블이 필요해지면 [[TEAM-PLAN]] 4.4 의 "테이블 추가" 절차를
타야 하고, `pipeline/tables.yaml` 과 `db/erd.py` 의 DOMAINS 를 함께 고쳐야 한다.
**합성 데이터 작업과 같은 PR 에 넣지 않는다.**
