# 핵심 지표를 10개로 고정한다

**결정** — 마트(P6)를 설계하기 전에 지표를 먼저 못 박는다. 표를 만들고 나서
"이걸로 뭘 볼까"를 묻지 않는다. **지표가 표의 그레인을 정한다.**

## 무엇을 재나

이 서비스의 루프는 하나다 —
**투표(하트 적립) → 상대가 받은 투표를 얻음 → 궁금해서 하트를 씀(힌트) →
하트가 마름 → 광고·충전·다시 투표.** 공급과 수요가 **같은 유저 풀 안**에
있어서, 지표도 루프의 마디마다 하나씩 잡는다.

**North Star — 주간 투표 완주자.** `vote_session.status = 'COMPLETED'` 의
주별 고유 유저. 가입·해금·잔존·참여가 전부 여기 모이고, **이번 주 완주 수가
곧 다음 주 `vote_received` 물량**(수요이자 매출 원재료)이다.

| # | 지표 | 근거 컬럼 |
|---|---|---|
| 1 | 온보딩 완료 가입자 | `app_user.created_at` — 익명 계정 생성이 아니라 `complete_onboarding()` 시점 |
| 2 | 게이트 통과율 · 소요일 | `service_unlocked_at` / `created_at` |
| 3 | 활성화 전환율 | 해금 유저 중 완주 세션 ≥1 |
| 4 | 투표 세션 완주율 | `COMPLETED` / 전체 `vote_session` |
| 5 | 리텐션 2종 (접속·투표) | `user_session` vs `vote_session` |
| 6 | 받은 투표 열람률 | `vote_received.is_read` |
| 7 | FULL_NAME 전환율 · 광고 대체율 | `hint_purchase` |
| 8 | 하트 수지 (적립 vs 소비) | `heart_transaction` × `is_credit` |
| 9 | 민감 카테고리 신고율 | `report` × `question_category.is_sensitive` |

**다섯으로 줄이면** North Star · 2 · 5 · 6 · 8. 입구·병목·유지·수요·경제를
하나씩 덮는다.

## 7번은 한 번 틀렸다 — 기록해 둔다

처음에 "**200→300→500→1000 누진 요금의 단계별 이탈**"로 적었다. 그 요금제는
W14 가 없앤 것이고, 근거로 삼은 것은 `db/ddl/` 의 **낡은 주석**이었다
([[ddl-comments-rot-with-migrations]]).

현행은 기본 5종 각 20하트(순서 없음) + FULL_NAME 100하트(기본 3개 이상 연 뒤).
**순서가 자유롭고 기본 5종이 같은 값이라 "단계별 이탈"이라는 개념 자체가 없다.**
대신 구조가 더 나은 질문을 준다 — **3개 게이트를 넘은 사람 중 몇 %가 100하트를
지르는가**. 게이트가 퍼널을 깨끗이 잘라준다.

⚠️ 구 서비스의 누진 요금은 **벤치마크로도 쓰지 않는다.** 단가가 10배 달라
하트 경제가 다른 체제다 — 생성기가 투표 적립을 실측 5~15 에서 2~7 로 낮춘 것도
같은 이유다.

## 일간 모니터링에는 리텐션율을 쓰지 않는다

코호트 리텐션은 **시차가 구조적**이다. 오늘 코호트의 D30 은 30일 뒤에 나오고,
클로즈드 테스트 초기에는 **D30 코호트가 존재하지도 않는다.** 매일 보는 자리에
진단 지표를 놓은 꼴이다.

대신 **DAU 를 상태로 쪼갠다** — 신규 / 잔존 / 복귀 / 이탈. 셋을 더하면 그냥
DAU 라 직관성을 잃지 않는데, "같은 100명인가 다른 100명인가"가 드러나고
**시차가 없다.** 주간에는 WAU/MAU 하나만 더한다.

코호트 리텐션은 버리지 않는다 — **대시보드가 아니라 분석 자리**로 옮긴다.
합성 v5(20,000명)에서는 여전히 본체다.

**대안** — "접속자 수만 본다"를 검토하고 기각했다. 수는 결과값이라 **무엇이
변했는지는 알려주지만 왜인지는 못 알려준다.** 40명이 빠지고 40명이 들어와도
평평하다. 다만 **실유저(20~50명)에는 이 지적이 맞다** — 30명 코호트는 한 명에
3.3%p 가 튄다. 실유저 쪽은 비율을 버리고 절대수로 본다.

## 마트에 주는 영향

지표 9개가 표 **3장**으로 접힌다.

| 마트 | 그레인 | 덮는 지표 |
|---|---|---|
| `mart_user_lifecycle` | user_id 1행 | 가입·해금·첫투표·제재·탈퇴 시각 → 1·2·3 |
| `mart_user_daily` | user_id × date(KST) | 접속·완주·받은투표·열람·힌트·하트 → 4·5·6·7 |
| `mart_heart_daily` | date × `type_code` | 8 |

`mart_user_daily` 에 **`user_state`(NEW/RETAINED/RESURRECTED/DORMANT) 한 컬럼**을
둔다. 이것 하나로 일간 모니터링과 코호트 리텐션이 **같은 표에서** 나온다 —
마트를 두 벌 만들지 않는다.

표준 필터와 KST 변환은 [[ops-analysis-conventions]] 를 따른다.

## 아직 정하지 않은 것

- **9번의 분모.** 신고 수 / 출제 수인지, 신고 수 / 노출 수인지. `report` 는
  실서비스에 아직 거의 없고, 이 지표를 켜려고 외모 질문을 연 것이므로
  실데이터가 쌓인 뒤에 정한다.
- **결제 지표는 뺐다.** 실서비스 결제는 전부 `MVP-STUB-` 스텁이라 존재하지
  않는다. 합성 데이터 한정으로만 ARPPU 를 본다.
