# 민감 질문에 신고 성향을 심는다 — 안 심으면 플래그가 아무 의미도 없다

**결정** — 신고 대상 질문을 고를 때 `is_sensitive` 인 질문에 **3.5배 가중치**를
준다(`moderation.sensitive_report_multiplier`).

**이유** — [[appearance-questions-for-report-rate]] 에서 외모 카테고리를 연
목적은 **"민감한 질문이 실제로 얼마나 신고되는지"를 재는 것**이었다.
그런데 생성기가 신고 대상을 `rng.choice(self.questions)` 로 **완전 균등하게**
골랐다. 결과는 이랬다.

| | v1 (균등) | v2 (가중) |
|---|---|---|
| APPEARANCE | 0.439 / 1천건 | **1.193** |
| 최하위 카테고리 | 0.379 | 0.331 |
| **차이** | **1.16배 — 노이즈** | **3.4배** |

8개 카테고리가 0.379~0.439 사이에 촘촘히 모여 있었다. **순위 차이가 노이즈였고,
`is_sensitive` 플래그가 데이터에서 아무 의미도 갖지 못했다.**

카테고리를 열어 질문 16개를 만들어 놓고도 **목적은 달성되지 않은 상태**였다.

## 왜 몰랐나 — 질문 dict 에 민감도가 없었다

`gen_questions()` 가 `self.questions` 에 담는 것이 `{"id", "scope"}` 뿐이었다.
`gen_moderation()` 은 카테고리를 알 방법이 없었다. `code` 와 `sensitive` 를
함께 담도록 고쳤다.

**대안** — 배수를 더 크게(10배 등) 주는 안을 기각했다. 그러면 "민감 질문은
거의 다 신고된다"가 되어 신고 사유 분석이 한쪽으로 쏠린다. 3.5배면
**뚜렷하되 다른 카테고리도 살아 있다.**

**영향**

- 이제 <b>`is_sensitive` 플래그를 데이터로 검증할 수 있다</b> —
  "민감 표시된 질문이 실제로 더 신고되는가"에 답할 수 있고, 신고 파이프라인의
  민감도별 처리를 시험할 재료가 생겼다.
- ⚠️ 이 배수는 **우리가 정한 값**이다. 실서비스의 실제 배수가 아니다.
  합성 데이터로는 "그런 구조가 있을 때 분석이 성립하는가"만 확인하고,
  **실제 배수는 실데이터로 재야 한다.**
