# 합성 데이터를 전부 지운다 — 낡아서

**결정** — 합성 데이터를 사는 곳 세 군데에서 전부 지웠다.

| 지운 것 | 규모 |
|---|---|
| BigQuery `raw` 의 `_source='local'` | 26테이블 · 7,863,066행 |
| `_load_state` 의 `local` 워터마크 | 28개 |
| 로컬 `pgtest` 컨테이너 | 통째로 |
| `data/synthetic/*.csv` | 411MB · 20파일 |

Supabase 는 손대지 않았다. 애초에 합성이 0행이었다 — 더미 친구는 진작에 정리됐다.

**이유는 정리가 아니라 틀려서다.** 마지막 생성이 7월 29일인데 그 뒤로
마이그레이션 004~010 이 들어갔다. 합성 분면에는 `is_admin` 도 `reply_text` 도
없고, 힌트 구조가 아예 다르고(순차 4단계 시절), `vote_item.padded_count` 가
786만 행 전부 NULL 이고, 이제 없는 `admin_user` 5행이 남아 있었다.

**그걸로 분석하면 틀린 답이 나온다.** 보관 가치가 0이 아니라 마이너스였다.
재생성이 2분(생성 25초 + 적재 89초)인 것이 결정을 쉽게 만들었다.

**대안**
- 다시 만들어 덮어쓴다. 기각 — 순서만 바꾼 게 아니다. [[TEAM-PLAN]] 의 순서가
  *스키마 점검 → ERD 기반 데이터 생성*이고 지금이 그 점검이 막 끝난 지점이다.
  혼자 만들어봤자 팀이 스키마를 또 건드리면 두 번 일이 된다.
- 낡은 채로 둔다. 기각 — 남아 있는 게 제일 나쁘다. 팀원이 그걸 진짜로 착각한다.

**⚠️ 워터마크를 함께 지운 것이 핵심이다.** 행만 지우고 `_load_state` 를 남겼으면
다음 로컬 적재 때 증분이 **"이미 최신"이라 판단해 아무것도 안 올리고 조용히
끝난다.** 에러도 안 난다. 이 프로젝트가 계속 물려온 종류의 실패다.

**BigQuery raw 를 지운 것은 원칙에 어긋나지 않는다.** raw 는 이력을 잃지 않는
층이지만, 합성은 **이력이 아니라 재생성 가능한 산출물**이다. 원천이 사라진
실유저 삭제 이력과는 성격이 다르다.

**남긴 것** — `generator/` 와 설정. 스키마와 어긋난 곳이 없는 것을 확인했다
(생성기가 쓰는 15개 표가 전부 살아 있는 스키마에 있다). 다시 만들 수 있다.

**남은 값** — raw 가 450MB → **2.9MB**, 실유저 35,951행. 팀원에게 보여주기엔
빈약해 보일 수 있으나 그게 사실이고, 2분이면 채운다.
