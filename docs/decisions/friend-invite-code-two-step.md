# 친구 맺기는 초대 코드로만, 요청·수락 2단계로

**결정** — 상대를 지목하는 수단은 초대 코드 하나다. 닉네임 검색은 넣지 않는다.
맺어지는 절차는 요청 → 수락이며, `friend_request` 와 `friendship` 의 직접 쓰기는
클라이언트에서 회수하고 `send_friend_request` / `accept_friend_request` /
`reject_friend_request` RPC 로만 처리한다.

**이유** — `app_user.id` 는 1부터 이어지는 정수다. `friend_request` INSERT 가
열려 있으면 `receiver_id` 를 1,2,3… 으로 바꿔가며 전체 가입자에게 요청을 뿌릴 수
있다. "코드를 아는 사람만 서로를 찾는다"는 전제가 통째로 무너진다.
수락 단계를 두는 이유는 잘못 입력한 코드나 원치 않는 상대가 조용히 친구가 되지
않게 하기 위해서다.

**대안** — 닉네임 검색. 기각. 닉네임에 UNIQUE 가 없어 동명이인을 구분하려면
소속을 함께 보여줘야 하는데, 그러면 "닉네임 + 학교 + 반"이 조회 가능한 명부가 된다.
개인정보를 받지 않기로 한 설계를 우회로 되돌리는 셈이다. 구 서비스 차단 사유 1위가
"모르는 사람임"(49.5%)이었던 것도 근거다.

**영향**
- 서로 코드를 주고받으면(양쪽 다 PENDING 요청을 만들면) 수락을 기다리지 않고
  그 자리에서 맺어진다. 둘 다 의사를 밝힌 상태이기 때문이다.
- 5명 게이트(`service_unlocked_at`)는 **수락 시점**에 찍는다. 보낸 것만으로 열리면
  혼자 계정을 만들어 통과할 수 있다.
- `friend_count` 는 증감이 아니라 `friendship` 을 세서 덮어쓴다(`refresh_friend_state`).
  구 서비스의 친구 수는 증감식이라 실제 관계와 어긋나 있었다.
- 거절당한 뒤 다시 보내면 요청이 되살아난다. 오타로 거절한 상대를 영영 다시 부를 수
  없게 만들지 않기 위해서다.
- 요청 목록에는 `my_friend_request` 뷰가 필요했다. 아직 친구가 아닌 상대의 닉네임을
  보여줘야 하는데 `app_user` 도 `friend_profile` 도 그 사람을 보여주지 않는다.
