# 실유저와 합성 데이터를 같은 BigQuery 테이블에 `_source` 로 섞는다

**결정** — 원천이 둘(Supabase 실유저 / 로컬 합성)이지만 BigQuery 에서는 같은
테이블 하나다. 적재할 때 `_source` 컬럼을 붙이고, 키를 `(_source, id)` 로 쓴다.

**이유** — 둘 다 `id` 가 1부터 이어지는 identity 다. 그대로 섞으면 실유저 1번과
합성 1번이 **서로를 덮어쓴다.** 테이블을 나누면 이 문제는 없지만 분석 쿼리가
전부 두 벌이 되고, "합성으로 검증한 쿼리를 실데이터에 그대로 돌린다"는
이 프로젝트의 전제가 깨진다.

**대안** — `app_user.is_synthetic` 플래그로 구분. 기각. 그 컬럼은 `app_user` 에만
있어서 나머지 41개 테이블에는 쓸 수 없고, id 충돌도 해결하지 못한다.

**영향**
- 분석에서 실유저만 보려면 `WHERE _source = 'supabase'` 다.
- 워터마크도 원천별로 따로 관리한다 (`raw._load_state`).
- `_loaded_at` 도 함께 남긴다. 언제 들어온 행인지가 파이프라인 자체의 분석 대상이다.
