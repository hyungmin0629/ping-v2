# 프로필 수정도 RPC 하나로 — 직접 UPDATE 권한 회수

**결정** — `update_profile()` 로만 닉네임·성별·소속을 바꾼다. W1 에서 열어둔
`GRANT UPDATE (nickname, class_id, gender) ON app_user` 를 회수했다.

**이유** — 그 권한 자체는 안전했다. 컬럼 단위로 제한돼 있어 `heart_balance` 나
`is_synthetic` 은 건드릴 수 없었다. 문제는 **검증이 없다**는 것이었다.

가입은 `complete_onboarding()` 이 닉네임 2~20자, 성별 필수, 학급 존재를
확인한다. 그런데 직접 UPDATE 는 그 규칙을 전부 우회했다.

| 우회 | 결과 |
|---|---|
| `nickname = ''` | 빈 이름으로 게시판에 글이 올라간다 |
| `gender = NULL` | 힌트 4단계 중 첫 단계(성별)가 사라진다 |
| `class_id` 아무거나 | 학급이 없는 학교로 옮겨 반을 못 고르는 상태가 된다 |

**가입과 수정이 같은 규칙을 따라야 한다.** 두 곳의 기준이 갈리면 어느 쪽이
맞는지 알 수 없다. 통로를 하나로 모으고 직접 권한은 닫았다 — 남겨두면
RPC 의 검증이 우회 가능해 있으나 마나가 된다.

**대안** — 직접 UPDATE 를 두고 트리거로 검증. 기각. 이 프로젝트는 "규칙이 있는
쓰기는 RPC 로"가 이미 확립된 규칙이고, 검증 위치를 둘로 나눌 이유가 없다.

**영향**
- 소속은 `selectable_school` 안으로 제한된다. FK 만 믿으면 전국 5,724개 학교
  아무 데나 갈 수 있는데, 학급이 없는 학교로 가면 반을 고를 수 없다.
- **학교를 옮기면 게시판과 친구 추천이 새 학교 기준으로 바뀐다.** 이미 쓴 글은
  옛 학교에 남고 본인도 더는 볼 수 없다. 글은 그 학교 사람들에게 남긴 것이지
  글쓴이를 따라다니는 것이 아니라고 보았다. 화면이 누르기 전에 이 사실을 알린다.
- **닉네임을 바꾸면 과거 글과 댓글에도 새 이름이 보인다.** `board_post` 뷰가
  `app_user` 를 그때그때 조인하기 때문이다. 이름 변경 이력은 남기지 않는다 —
  지금 필요하지 않고, 필요해지면 그때가 이력 테이블을 만들 때다.
- 화면은 온보딩 폼을 재사용한다. 학교 검색과 반 선택이 통째로 같아서, 복사하면
  학교 목록 규칙이 바뀔 때 한쪽만 고치는 사고가 난다.
