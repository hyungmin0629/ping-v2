# 행수 가드레일을 실측으로 다시 잡는다 — 위험은 행수가 아니라 쿼리량이다

**결정** — 총 행수 상한을 **4,000만 → 1억**으로 올린다(CSV 6GB). 대신 조건 둘을
단다 — **Looker 를 raw 에 직접 붙이지 않는다**(P6 stg/mart 선행),
**GCP 예산 알림을 켠다.**

**이유** — 4,000만은 근거 없이 잡은 값이었다. 규모를 두 방향으로 늘려 재보니
전제가 틀렸다.

| 조건 | 행수 | 유저당 |
|---|---|---|
| 500명 · 1개월 · 6교 | 1,149,566 | 2,299 |
| 2,000명 · 3개월 · 20교 | 6,011,787 | 3,006 |

**기간은 행수를 거의 안 늘린다.** 유저 4배 × 기간 3배 = 12배인데 실제로는 5.2배였다
([[activity-by-retention-tier]] 가 이유다). 기간 효과는 대략 `개월^0.25` 다.
20,000명·12개월 추정은 **8,500만 행 · BigQuery 3.5~5GB** 로, 무료 저장 한도
10GB 의 절반이다.

**대안** — 가드레일을 지키려고 유저 수를 줄이는 안을 기각했다. 유저를 줄이면
학교당 인원이 줄고 **학급당 인원이 무너져 "같은 반 친구"를 뽑을 풀이 사라진다.**
학교를 넓게 펴는 대신 밀도를 지키기로 한 결정과 정면으로 부딪힌다.

**⚠️ 진짜 위험은 쿼리량이다** — Looker 대시보드가 raw 를 파티션 없이 직접 보면
`차트 20개 × 하루 30회 × 30일 = 18,000 쿼리`가 되고, 쿼리당 100MB만 스캔해도
1.8TB 로 무료 한도(1TB/월)를 넘는다. **행수는 위험 지표가 아니었다.**

**영향**

- [[TEAM-PLAN]] 5.2 의 "분석 착수 전 P6 선행" 제안이 비용 관점에서도 맞다는 것이
  확인됐다.
- 실질 병목은 비용이 아니라 **시간**이다. 8,500만 행이면 생성 ~12분, 로컬 적재
  40~70분, BigQuery 적재 20~40분 — **한 번 돌리는 데 1~2시간**이다.
  500명 → 2,000명 → 최종의 3단계를 지키는 이유가 이것이다.
