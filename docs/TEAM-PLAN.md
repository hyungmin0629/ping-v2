## 1. 요약

운영 서비스에 장애가 발생할 수 있다. 조건은 하나이며, 통제 가능하다.

> **로컬 DB 만 변경하고 Supabase 는 변경하지 않는다.**

주의할 점은 이 조건이 겉보기보다 지키기 어렵다는 것이다. **로컬과 Supabase 는
동일한 DDL 을 공유한다.** `db/ddl/` 과 `db/migrations/` 의 파일 하나가 두 환경에
모두 적용된다. 따라서 *"합성 데이터 전용 스키마 변경"은 성립하지 않으며*,
모든 스키마 변경은 잠재적인 운영 변경이다.

2026-07-30 기준 실사용자 6명이 서비스를 사용 중이며, 투표 40건과 게시글이
BigQuery 로 적재되고 있다.

## 2. 변경 유형별 영향 범위

코드를 확인한 결과다.

| 변경 유형 | 웹앱 | 파이프라인 | 위험도 |
|---|---|---|---|
| 컬럼 추가 | 영향 없음 | 자동 반영 | 낮음 |
| 컬럼 삭제·이름 변경 | 즉시 장애 | 값이 NULL 로 유입 | **높음** |
| 컬럼 타입 변경 | 장애 가능 | 적재 거부 | 중간 |
| 테이블 추가 | 영향 없음 | 적재 대상에서 누락 | 중간 |
| 제약(CHECK·UNIQUE) 추가 | RPC 실패 가능 | 영향 없음 | 중간 |
| 테이블 삭제 | 참조 화면 장애 | 기존 데이터 잔존 | **높음** |

**컬럼 추가가 안전한 근거** — 웹앱은 `select("*")` 를 사용하지 않는다. 모든 조회가
컬럼을 명시하므로 신규 컬럼은 애플리케이션에 노출되지 않는다. 파이프라인은 P4 에서
컬럼 자동 추가를 구현했다.

**컬럼 삭제가 위험한 근거** — 웹앱과 RPC 가 컬럼명을 직접 참조한다.
`db/rls/verify.py` 128항목이 대부분 검출하지만, 검출 시점은 이미 Supabase 에
적용한 이후다.

## 3. 식별된 위험 요소

위 표에 드러나지 않는 항목이다. 공통점은 **오류 없이 진행된다**는 점이다.

### 3.1 마이그레이션의 지연 적용

`db/apply.py` 는 `db/migrations/*.sql` 을 전부, 순서대로 적용한다. 스키마를
처음부터 재구성하기 위해 필요한 동작이지만 다음 경로가 발생한다.

1. 합성 데이터 작업용으로 `006_*.sql` 을 작성한다
2. 로컬에만 적용한다
3. 이후 임의 시점에 누군가 `apply.py --target supabase` 를 실행한다
4. **006 이 운영 환경에 반영된다**

마이그레이션 파일 작성은 곧 운영 반영 예약이다.

**조치 완료** — `apply.py --target supabase` 실행 시 현재 실사용자 수와 적용될
마이그레이션 목록을 출력하고 확인을 요구하도록 변경했다. 자동화에서는 `--yes` 로
건너뛴다.

### 3.2 신규 테이블의 적재 누락

`pipeline/tables.yaml` 에 등록되지 않은 테이블은 BigQuery 로 적재되지 않는다.
오류나 경고가 발생하지 않는다.

**조치 완료** — `pipeline/verify_load.py` 가 적재 검증 전에 매니페스트와 실제
스키마를 대조하고, 불일치 시 종료 코드 1 을 반환한다.

### 3.3 스키마 변경 시 증분 미검출

`ALTER TABLE ADD COLUMN` 은 트리거를 발동시키지 않으므로 `updated_at` 이
갱신되지 않는다. 결과적으로 증분 적재가 신규 컬럼을 반영하지 못하고 BigQuery 에
NULL 로 남는다. 2026-07-30 에 `vote_item.padded_count` 가 합성 데이터
803,187행 전부 NULL 이었던 원인이다.

**대응** — 컬럼 추가 후 해당 테이블을 `--full-refresh` 로 재적재한다.
자동화하지 않은 이유는 대상 테이블을 판단할 근거가 코드에 없기 때문이다.

## 4. 작업 절차

### 4.1 사전 준비 (팀원 각자, 약 20분)

저장소를 클론하고 [[ONBOARDING]] **A 갈래**를 완료한다. 클라우드 계정 없이
로컬에 40테이블과 합성 786만 행을 구성하고 정합성 검사 17종을 실행한다.

완료하지 못한 인원이 있으면 다음 단계로 진행하지 않는다.

### 4.2 Git 협업 규칙

| 규칙 | 근거 |
|---|---|
| `main` 직접 푸시 금지 | `main` 푸시는 Vercel 자동 배포로 이어진다. 실사용자가 있는 앱에 즉시 반영된다 |
| 브랜치 생성 후 PR 로 병합 | 스키마 변경을 최소 2인이 검토한다 |
| 초기 권한은 Read | 코드 열람과 분석에는 충분하다. 코드를 수정할 인원만 Write 로 상향한다 |

`.env` 와 `credentials.json` 은 공유하지 않는다. `SUPABASE_SERVICE_KEY` 는 RLS 를
우회하는 마스터 키다. 실데이터 접근이 필요한 경우 GCP 콘솔에서 **BigQuery 데이터
뷰어** 권한을 부여한다.

### 4.3 스키마 점검 (변경 없음)

이 단계에서는 조회만 수행한다.

- 카드형 ERD 로 전체 구조를 확인한다 (40테이블 341컬럼, `python db/erd.py` · `db/erd_board.py` 로 갱신)
- `db/ddl/*.sql` 의 주석을 확인한다. 각 테이블에 구 서비스의 어떤 결함을 차단하기
  위한 구조인지 실측치와 함께 기록되어 있다
- [[DECISIONS]] 를 확인한다. 기각된 대안과 그 근거가 기록되어 있으므로 검토
  완료된 안을 재논의하는 비용을 줄일 수 있다

**산출물** — 변경 후보 목록. 항목마다 변경 사유와 "해당 변경이 없을 경우 수행
불가능한 분석"을 명시한다.

### 4.4 변경 범위 결정

변경 후보를 다음 기준으로 분류한다.

| 분류 | 처리 방식 |
|---|---|
| 생성기 파라미터로 해결 가능 (분포·규모·상관관계) | 스키마 변경 없음. 즉시 진행 |
| 컬럼 추가 | 마이그레이션 1건. 위험도 낮음 |
| 컬럼 삭제·이름 변경·타입 변경 | 웹앱 수정 동반. **별도 작업 단위로 분리** |
| 테이블 추가 | `pipeline/tables.yaml` 및 `db/erd.py` 의 DOMAINS 동시 갱신 |

**원칙** — 합성 데이터 품질 개선을 위해 운영 스키마를 변경하지 않는다. 분포의
비현실성은 대부분 `generator/config/distribution.yaml` 의 문제이며 스키마 문제가
아니다.

스키마 변경을 확정한 경우 [[DECISIONS]] 에 결정·이유·대안·영향을 기록한다.

### 4.5 데이터 생성 및 로컬 검증

```bash
python generator/generate.py
python generator/load.py --truncate          # 95·96 자동 실행
docker exec -i pgtest psql -U postgres -d pingv2 \
  -c "SET max_parallel_workers_per_gather = 0;" -f - < qa/checks/integrity.sql
```

정합성 검사 17종이 전부 0건이어야 다음 단계로 진행한다. 위반이 발생하면 생성기
결함이다.

### 4.6 BigQuery 적재

```bash
python pipeline/extract_load.py --source local --full-refresh
python pipeline/verify_load.py  --source local
```

`--full-refresh` 는 `_source='local'` 행만 삭제 후 재적재하므로 실사용자
데이터에 영향을 주지 않는다.

### 4.7 분석 및 시각화

raw 계층을 직접 조회할 경우 다음 세 조건이 항상 필요하다. 누락 시 오류 없이
잘못된 결과가 산출된다.

```sql
WHERE _source = 'supabase'      -- 누락 시 합성 데이터 5,000명이 혼입
  AND _deleted_at IS NULL       -- 누락 시 삭제된 계정이 혼입
-- 조인 시에도 _source 조건 필요 (두 원천의 id 가 중복된다)
```

## 5. 절차상 제안

### 5.1 점검과 변경 사이에 판단 단계를 둔다

기존 계획은 "스키마 점검 → 데이터 생성" 순서였다. 이 경우 점검 과정에서 도출된
개선안이 곧바로 마이그레이션으로 이어지고, 3.1 의 경로를 통해 운영에 반영된다.
4.4(변경 범위 결정)를 별도 단계로 두는 것을 제안한다.

### 5.2 분석 착수 전에 P6(stg 계층)을 선행한다

4.7 의 세 조건을 분석자가 매번 기억해야 하는 구조이며, 누락 시 오류가 발생하지
않는다. stg 계층에서 사전 필터링하면 해당 실수의 발생 여지가 제거된다.

2026-07-30 실제 사례 — "금일 투표 수" 조회 시 삭제된 데이터가 포함되어 실제
0건이 20건으로 집계되었다. 쿼리는 정상 종료되었다.
