# 팀 작업 계획 — 스키마 점검부터 분석까지

2026-07-30 작성. 팀원과 합성 데이터를 다시 만들기로 하면서, **그 과정이 지금
돌아가는 서비스를 깨뜨리지 않는지** 확인하고 절차를 정리한 문서다.

관련: [[CLAUDE]] · [[DECISIONS]] · [[ONBOARDING]] · [[erd]]

---

## 0. 먼저, 결론

**서비스가 터질 수 있다. 다만 조건이 하나뿐이고, 그 조건은 지키기 쉽다.**

> **로컬 DB 만 건드리고 Supabase 는 건드리지 않는다.**

그런데 이 조건이 생각보다 미묘하다. **로컬과 Supabase 는 같은 DDL 을 공유한다.**
`db/ddl/` 과 `db/migrations/` 하나가 두 곳에 다 적용된다. 그래서
*"합성 데이터용 스키마 변경"이라는 것은 존재하지 않는다* —
모든 스키마 변경은 **잠재적인 실서비스 변경**이다.

지금 실유저 6명이 실제로 쓰고 있다(2026-07-30 기준). 투표 40건, 게시글 2건이
쌓였고 BigQuery 로 흐르고 있다.

---

## 1. 무엇이 깨지고 무엇이 안 깨지나

변경 종류별로 실제 영향 범위를 확인했다. 추측이 아니라 코드를 뒤져 확인한 결과다.

| 변경 | 웹앱 | 파이프라인 | 위험 |
|---|---|---|---|
| **컬럼 추가** | 영향 없음 | 자동으로 따라감 | 🟢 낮음 |
| **컬럼 이름 변경·삭제** | **즉시 깨짐** | 조용히 NULL | 🔴 높음 |
| **컬럼 타입 변경** | 깨질 수 있음 | **적재 거부** | 🟠 중간 |
| **테이블 추가** | 영향 없음 | **조용히 누락** | 🟠 중간 |
| **제약(CHECK·UNIQUE) 추가** | RPC 가 걸릴 수 있음 | 영향 없음 | 🟠 중간 |
| **테이블 삭제** | 쓰는 화면이 있으면 깨짐 | 유령으로 남음 | 🔴 높음 |

**컬럼 추가가 안전한 이유** — 웹앱이 `select("*")` 를 한 군데도 안 쓴다.
전부 `select("id, nickname, ...")` 처럼 컬럼을 명시한다. 새 컬럼은 앱에 보이지도
않는다. 파이프라인도 P4 에서 자동 추가를 붙여뒀다.

**컬럼 삭제가 위험한 이유** — 앱과 RPC 가 그 이름을 직접 쓴다.
`db/rls/verify.py` 128항목이 대부분 잡아주지만, **잡아준다는 건 이미 Supabase 에
적용한 뒤**라는 뜻이다. 그 시점엔 이미 늦다.

## 2. 진짜 지뢰 세 개

위 표보다 이쪽이 더 중요하다. **조용히 터지는 것들**이다.

### 지뢰 ①  마이그레이션은 나중에 저절로 실서비스에 간다

`db/apply.py` 는 `db/migrations/*.sql` 을 **전부, 순서대로** 적용한다.
대상이 로컬이든 Supabase 든 똑같이.

> 팀원이 합성 데이터용으로 `006_something.sql` 을 만든다 → 로컬에만 적용한다 →
> 몇 주 뒤 누군가 `python db/apply.py --target supabase` 를 돌린다 →
> **006 이 실서비스에 조용히 적용된다.**

의도한 동작이다(그래야 스키마를 처음부터 다시 만들 수 있다). 하지만
"로컬에만 적용했으니 괜찮다"는 착각을 부른다. **마이그레이션 파일을 만드는
순간 그것은 실서비스 예약이다.**

### 지뢰 ②  새 테이블은 파이프라인에서 조용히 빠진다

`pipeline/tables.yaml` 에 없는 테이블은 **BigQuery 로 아예 안 간다.**
오류도 경고도 없다. 지금은 42개가 정확히 맞지만 자동 검사가 없다.

### 지뢰 ③  스키마를 바꿔도 증분은 아무것도 잡지 않는다

`ALTER TABLE ADD COLUMN` 은 트리거를 발동시키지 않아 `updated_at` 이 그대로다.
그래서 새 컬럼이 BigQuery 에 **전부 NULL 로** 남는다.
2026-07-30 에 `vote_item.padded_count` 가 합성 803,187행 전부 NULL 이었던
이유가 이것이다. 컬럼을 추가한 뒤에는 그 테이블을 `--full-refresh` 해야 한다.

## 3. 제안하는 절차

작업자가 말한 순서에 **빠진 단계를 채워 넣은** 것이다.
원래 순서: 깃 협업 → 스키마 점검 → ERD 기반 논의 → 데이터 생성 → 적재 → 분석·시각화

### 0단계 · 준비 (팀원 각자, 20분)

각자 저장소를 클론하고 [[ONBOARDING]] **A 갈래**만 끝낸다.
계정 없이 로컬에 42테이블 + 합성 786만 행이 서고, 정합성 17종이 돈다.
**여기까지 안 되는 사람이 있으면 다음으로 넘어가지 않는다.**

### 1단계 · 깃 협업 규칙 정하기

| 규칙 | 이유 |
|---|---|
| `main` 에 직접 푸시하지 않는다 | **`main` 푸시 = Vercel 자동 배포.** 실유저 6명이 쓰는 앱이 바로 바뀐다 |
| 브랜치를 파고 PR 로 합친다 | 스키마 변경을 한 명이라도 더 보게 만든다 |
| 팀원 권한은 처음에 **Read** | 코드 읽고 분석하는 데는 충분하다. 고칠 사람만 Write 로 올린다 |

⚠️ **`.env` 와 `credentials.json` 은 절대 주고받지 않는다.**
`SUPABASE_SERVICE_KEY` 는 RLS 를 통째로 무시하는 키다.
실데이터가 필요하면 GCP 콘솔에서 **BigQuery 데이터 뷰어** 권한을 주는 쪽이 맞다.

### 2단계 · 스키마 점검

**읽기만 한다. 이 단계에서는 아무것도 바꾸지 않는다.**

- 카드형 ERD 로 전체를 본다 (42테이블 355컬럼, `python db/erd.py` 로 갱신)
- `db/ddl/*.sql` 의 **주석**을 읽는다. 각 테이블 위에 "구 서비스의 어떤 결함을
  막으려고 이 구조가 됐는지"가 실제 수치와 함께 적혀 있다
- [[DECISIONS]] 를 읽는다. **왜 그렇게 안 했는지**가 거기 있다.
  이미 검토하고 기각한 안을 다시 제안하는 데 시간을 쓰지 않기 위해서다

**산출물**: 바꾸고 싶은 것 목록. 각 항목에 "왜"와 "그게 없으면 어떤 분석을
못 하는가"를 적는다.

### 3단계 · 무엇을 바꿀지 정하기 — **여기가 관문이다**

바꾸고 싶은 것 하나하나를 아래로 분류한다.

| 분류 | 처리 |
|---|---|
| **생성기만 고치면 되는 것** (분포·규모·상관관계) | 스키마 안 건드림. 🟢 바로 진행 |
| **컬럼 추가** | 마이그레이션 1개. 🟢 위험 낮음 |
| **컬럼 삭제·이름 변경·타입 변경** | 🔴 **웹앱 수정이 함께 필요.** 별도 단계로 뺀다 |
| **테이블 추가** | `pipeline/tables.yaml` · `db/erd.py` DOMAINS 도 함께 |

**원칙: 합성 데이터를 잘 만들려고 실서비스 스키마를 바꾸지 않는다.**
분포가 현실적이지 않은 것은 대부분 `generator/config/distribution.yaml` 문제이지
스키마 문제가 아니다.

정말 스키마를 바꿔야 한다면 [[DECISIONS]] 에 결정·이유·대안·영향을 적는다.

### 4단계 · 데이터 생성과 로컬 검증

```bash
python generator/generate.py
python generator/load.py --truncate          # 95·96 자동 실행
docker exec -i pgtest psql -U postgres -d pingv2 \
  -c "SET max_parallel_workers_per_gather = 0;" -f - < qa/checks/integrity.sql
```

**정합성 17종이 전부 0이어야 다음으로 간다.** 하나라도 걸리면 생성기 문제다.

### 5단계 · BigQuery 적재

```bash
python pipeline/extract_load.py --source local --full-refresh
python pipeline/verify_load.py  --source local
```

`--full-refresh` 는 `_source='local'` 행만 지우고 새로 넣는다.
**실유저 데이터는 건드리지 않는다.**

### 6단계 · 분석·시각화

분석 쿼리에는 **항상 세 가지**가 필요하다. 하나라도 빠지면 조용히 틀린다.

```sql
WHERE _source = 'supabase'      -- 없으면 합성 5,000명이 섞인다
  AND _deleted_at IS NULL       -- 없으면 지운 계정이 섞인다
-- 조인할 때도 _source 를 함께 (두 원천의 id 가 실제로 겹친다)
```

**P6 에서 stg 층을 만들면 이 셋이 미리 걸러져 실수할 자리가 사라진다.**
분석을 본격적으로 하기 전에 P6 을 먼저 하는 편이 낫다.

## 4. 지금 걸 수 있는 안전장치

문서로 "조심하자"고 적는 것은 오늘 하루에만 두 번 실패했다
(정합성 검사가 몇 주간 안 돌던 것, `safeupdate` 로 투표가 죽던 것).
**규칙은 코드로 내려야 지켜진다.**

| 안전장치 | 막는 것 | 비용 |
|---|---|---|
| `apply.py --target supabase` 에 확인 절차 | 지뢰 ① 실수 적용 | 10분 |
| `tables.yaml` ↔ 실제 테이블 대조를 `verify_load.py` 에 | 지뢰 ② 조용한 누락 | 20분 |
| GitHub 브랜치 보호 (`main` 직접 푸시 금지) | 사고성 배포 | 5분, 코드 아님 |

`db/rls/verify.py` 는 이미 소스 검사를 하고 있다(WHERE 없는 DELETE).
같은 자리에 위 검사를 붙이면 된다.

## 5. 요약 — 이 계획에 문제가 있는가

**없다. 다만 3단계(무엇을 바꿀지 정하기)를 원래 계획이 빠뜨리고 있었다.**

"스키마 점검 → 데이터 생성"으로 바로 가면, 점검하다 나온 아이디어가 곧장
마이그레이션이 되고 그게 실서비스 예약이 된다. **점검과 변경 사이에 판단을
한 번 넣는 것**이 이 문서의 핵심 제안이다.

그리고 순서를 하나 바꾸는 편이 낫다 —
**분석·시각화 전에 P6(stg 층)** 을 먼저 한다. 지금 raw 를 직접 조회하면
`_source`·`_deleted_at`·조인 키 세 가지를 매번 사람이 기억해야 하는데,
그 실수는 오류를 내지 않는다.
