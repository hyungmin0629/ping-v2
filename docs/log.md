# 작업 이력

위키에 **무엇을 언제 했나.** 덧붙이기만 하고 고치지 않는다.

git log 와 다르다 — git 은 파일이 어떻게 바뀌었는지를 남기고, 여기는
**원본을 반영했는지 · 색인을 다시 세웠는지 · 검사를 돌렸는지**를 남긴다.
회의록을 넣고 반영을 잊어버리는 것이 제일 흔한 사고라 그걸 잡는 것이 목적이다.

형식: `## [YYYY-MM-DD] 연산 | 한 줄`

연산은 셋이다 — `ingest`(원본을 읽어 위키에 반영) · `query`(물음에 답하고
답을 남김) · `lint`(어긋난 곳을 찾아 고침). 자세한 절차는 [[CLAUDE|CLAUDE.md]].

## [2026-08-25] 주간 보고서를 자동 발송으로 만들었다

샘플 PDF 를 받아 "매주 저절로 Drive 에 쌓이게" 만든 작업. `report/` 가 생겼다 —
쿼리 9개 · 수집(`collect.py`) · 렌더(`render.py`·`charts.py`·템플릿) ·

**실행 주체를 로컬 Airflow 가 아니라 GitHub Actions 로 정했다.** 착수 시점에
Docker 가 꺼져 있었고 raw 워터마크가 5일 밀려 있었다 — 로컬 스케줄러로는
"손대지 않아도 유지"가 성립하지 않는다는 것이 그 자리에서 증명된 셈이다.
적재부터 배송까지 일곱 단계를 CI 가 통째로 돈다([[weekly-report-runs-in-ci]]).

**샘플 레이아웃을 실유저 규모에 맞추는 것이 이 작업의 절반이었다.** 실유저는
23명이고 매출이 0원이라, 샘플의 "58.2%" 자리에 들어갈 숫자가 대부분 1/2 이나
0/3 이다. 레이아웃을 바꾸는 대신 **표기 규칙**을 넣었다 — 분모 10 미만이면
비율을 만들지 않는다([[weekly-report-suppresses-small-denominators]]).
유저가 늘면 같은 코드가 저절로 비율로 돌아선다.

같은 원칙을 그래프에도 적용했다. 분모가 없던 주는 0% 로 찍지 않고 **선을 끊는다** —
0% 로 그리면 "그 주에 아무도 투표하지 않았다"는 없던 사실이 생긴다.

**적체는 `mart_backlog_weekly` 대신 `mart_report` 에서 복원했다.** 그 마트는
첫 신고~마지막 신고 사이의 주만 행을 만드는데, 실유저는 신고가 3건뿐이라
8주 창에 한 주만 들어와 선 그래프가 끊겼다. 신고 1건=1행에서 주말 기준으로
다시 세면 어느 주든 복원된다.

첫 보고서가 드러낸 것: **신고 3건이 4주째 7일 이상 미처리로 밀려 있다.**
처리 화면(`sanction`)이 없어서 PENDING 으로 고이는 그 문제가 매주 1쪽에 뜬다.
