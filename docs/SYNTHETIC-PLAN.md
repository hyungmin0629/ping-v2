# 합성 데이터 설계 — 팀이 정할 것

스키마를 40테이블로 확정했다(2026-07-31). 이 문서는 **그 위에 어떤 합성 데이터를
만들 것인가**를 팀이 결정하기 위한 것이다.

옛 합성 데이터 786만 행은 [지웠다](DECISIONS.md) — 스키마가 바뀌어 낡았기 때문이다.
지금은 **아무것도 없는 상태**이고, 다음에 만드는 것이 사실상 첫 생성이다.

관련 문서 — 스키마는 [[erd]], 작업 절차는 [[TEAM-PLAN]], 결정 이력은 [[DECISIONS]].

---

## 0. 먼저 — 숫자부터 정하지 않는다

이 문서에서 제일 중요한 문장이다.

> **"유저 몇 명, 몇 개월"을 먼저 정하면 안 된다.**
> **"무슨 질문에 답할 데이터인가"를 먼저 정하고, 규모는 거기서 따라 나온다.**

파라미터가 40개쯤 되는데, 근거 없이 정하면 40번의 취향 대결이 된다. 반대로
"우리는 **이 다섯 개 질문**에 답할 것이다"를 먼저 합의하면, 대부분의 파라미터는
**답이 하나로 좁혀지거나 아무래도 상관없어진다.**

예를 들어 —

- "리텐션 곡선을 보겠다"면 **기간**이 중요하고 유저 수는 5,000이든 2,000이든 상관없다.
- "학교별 차이를 보겠다"면 **학교당 밀도**가 중요하고 총 기간은 짧아도 된다.
- "하트 경제가 인플레인지 보겠다"면 **지급·소비 비율**이 전부고 친구 그래프는 대충이어도 된다.

그래서 **1장을 먼저 결정한다.** 2장부터는 1장이 정해지면 절반은 자동으로 정해진다.

## 1. 【결정 1】 이 데이터로 무슨 질문에 답할 것인가

가장 중요하고, 가장 먼저 정해야 하고, **팀이 다 같이 정해야 하는 유일한 항목**이다.
나머지는 이것이 정해지면 대부분 따라온다.

후보를 적어 둔다. **3~5개를 고른다.** 다 고르면 아무것도 안 고른 것과 같다.

| # | 질문 | 이 질문에 답하려면 필요한 것 | 난이도 |
|---|---|---|---|
| Q1 | **왜 떠나는가** — 이탈 유저와 잔존 유저는 무엇이 달랐나 | 긴 기간(3개월+), 탈퇴 사유, 세션 로그 | 중 |
| Q2 | **친구 5명 게이트가 병목인가** — 게이트를 못 넘은 사람은 어디서 막혔나 | 친구 요청/수락/거절 전 과정, 게이트 미달 유저 | 낮 |
| Q3 | **하트 경제가 성립하는가** — 지급과 소비가 균형인가, 인플레인가 | 원장 전체, 힌트 구매, 충전 | 낮 |
| Q4 | **무엇이 궁금해서 하트를 쓰는가** — 어떤 힌트를 먼저 사는가 | 선택형 힌트 6종 구매 순서·조합 | 중 |
| Q5 | **투표가 재미있는가** — 완료율·셔플률·재방문 | 세션·문항·셔플·광고 | 낮 |
| Q6 | **학교/반 규모가 경험을 바꾸는가** — 작은 반 유저는 다르게 행동하나 | 학교 밀도 편차, 후보 부족(padded_count) | 높 |
| Q7 | **게시판이 투표를 돕는가** — 글 쓰는 사람이 투표도 많이 하나 | 게시판 생성기(**지금 없음**) | 높 |
| Q8 | **관계가 어떻게 끝나는가** — 친구를 끊는 사람은 어떤 사람인가 | 친구 끊기 생성기(**지금 없음**) | 중 |

**내 추천: Q2 · Q3 · Q5 를 기본으로, 여기에 Q1 또는 Q4 를 하나 더.**

이유 —

- **Q2·Q3·Q5 는 생성기가 이미 만든다.** 파라미터만 정하면 된다. 첫 사이클을
  빨리 돌려보는 것이 중요하다. 만들고 → 적재하고 → 분석해보고 → 파라미터를
  고치는 **한 바퀴를 먼저 완주**해야 무엇이 부족한지 알 수 있다.
- **Q1 은 이 프로젝트의 원점이다.** 구 서비스에서 탈퇴 기록에 유저 식별자가 없어
  못 했던 분석이 정확히 이거고, 새 스키마가 그걸 하려고 `user_withdrawal.user_id`
  를 NOT NULL 로 잡았다. 안 하면 스키마를 그렇게 만든 이유가 증명되지 않는다.
- **Q4 는 새로 만든 기능(W14 선택형 힌트)의 유일한 검증**이다. 순차 4단계를
  버리고 선택형으로 바꾼 판단이 옳았는지는 이 데이터로만 볼 수 있다.
- **Q6·Q7·Q8 은 1차에서 빼기를 권한다.** Q6 은 학교 밀도 분포를 새로 설계해야
  하고, Q7·Q8 은 생성기를 새로 써야 한다. 1차를 완주한 뒤 2차에 넣는다.

> ✍️ **정할 것:** 고른 질문 번호 ______ / 뺀 이유 ______

## 2. 지금 생성기가 어디까지 만드나 — 출발점

정하기 전에 **현재 상태**를 알아야 한다. 좋은 소식과 나쁜 소식이 반반이다.

### 2-1. 만드는 표 16개 / 안 만드는 표 24개

```
만든다  region school grade_class app_user user_session user_withdrawal
        friend_request friendship question question_request
        vote_session vote_item vote_candidate vote_shuffle vote_received
        hint_purchase heart_purchase heart_transaction ad_impression

안 만든다  post post_comment post_like comment_like          ← 게시판 (W9)
          rejected_friend_recommendations                    ← 추천 거절 (W10)
          report sanction block_record                        ← 신고·제재·차단
          meal_plan meal_menu_item school_event               ← NEIS 가 채운다
          timetable school_notice school_notice_read          ← 아직 수집기 없음
          (그 외 마스터 표 7개는 90_seed_master.sql 이 채운다)
```

### 2-2. ⚠️ 만들기는 하는데 **옛 서비스를 그린다**

여기가 진짜 문제다. 생성기는 **돌아간다.** 그런데 지금 돌리면 **이제 존재하지
않는 서비스의 데이터**가 나온다. 오류가 안 나서 더 위험하다.

| 무엇 | 생성기가 만드는 것 | 지금 서비스 | 고쳐야 하나 |
|---|---|---|---|
| 힌트 요금 | 누진 **200 → 300 → 500 → 1000** | **20 × 5종 + 이름 100** | **반드시** |
| 힌트 종류 | INITIAL/GENDER/CLASS/FULL_NAME 4종 | + **MEDIAL·FINAL** 6종 | **반드시** |
| 힌트 순서 | `step` 1~4 **순차** | 순서 없음, **골라 산다** | **반드시** |
| `char_index` | NULL | 자모 힌트는 어느 글자인지 필요 | **반드시** |
| 광고 무료 힌트 | 없음 | 성별은 광고 30초로도 (1일 1회) | 권장 |
| 1회성 답장 | 없음 (`reply_text` NULL) | 20하트·30자·한 번 | 권장 |
| 친구 끊기 | 없음 (`ended_at` NULL) | 있음 (W19) | 선택 |
| 하트 충전 | 실제 결제 모델 | **스텁**(무료·1일 1회) | 결정 필요 |

**`hint_cost_steps: [200, 300, 500, 1000]` 이 그대로 있는 한, Q3(하트 경제)과
Q4(무엇이 궁금한가)는 답이 전부 틀린다.** 요금이 10배 다르다.

> ✍️ **정할 것:** 위 표에서 **반드시**를 넘어 어디까지 고칠 것인가

## 3. 근거가 어디서 오는가 — 세 갈래

파라미터마다 근거의 성격이 다르다. **이걸 구분하지 않으면 추측을 실측처럼
다루게 된다.**

| 갈래 | 무엇 | 신뢰도 | 쓸 수 있는 곳 |
|---|---|---|---|
| **A. 구 서비스 실측** | 67만 유저의 실제 로그 | 높음 | 옛 서비스에도 있던 기능 |
| **B. 우리 실유저** | 지인 **23명**, 열흘치 | **낮음(표본)** | 새 기능의 **유일한** 근거 |
| **C. 근거 없음** | 아무 데도 없다 | — | 우리가 정한다 |

**갈래 B 의 한계를 분명히 해둔다.** 23명은 통계가 아니다. 그런데 선택형 힌트,
답장, 게시판, 친구 끊기는 구 서비스에 **아예 없던 기능**이라 A 를 쓸 수 없다.
B 아니면 C 다.

### 3-1. 우리 실유저 23명 실측 (2026-07-31)

숫자를 그대로 옮긴다. **참고는 하되 그대로 쓰지 말 것.**

| 지표 | 값 | 읽을 때 주의 |
|---|---|---|
| 유저 | 23명 | 전부 지인. 서로 친구 |
| 친구 수 중앙값 | **17명** | 구 서비스 실측 30명보다 적다. 폐쇄 집단이라 그렇다 |
| 유저당 투표 세션 | 3.4회 | 열흘치. 기간이 짧다 |
| 세션당 문항 | 10.0 | 설정값 그대로(고정) |
| 문항 완료율 | **86.3%** | 구 서비스 96.3%보다 낮다 |
| 셔플 비율 | **2.5%** | 설정값 18%와 **7배 차이** |
| 받은 투표 열람률 | **73.1%** | 구 서비스 55.5%보다 높다 (지인이라 궁금) |
| 받은 투표 중 힌트 구매 | 8.7% | |
| 받은 투표 중 답장 | **0.3%** | 어제 만든 기능이라 거의 안 쓰임 |
| 탈퇴 | **0명** | 지인이라 안 나간다. 이탈 모델링에 못 쓴다 |
| 친구 끊기 | **0건** | 위와 같다 |

**힌트 종류별 구매 (새 모델의 유일한 실측)**

```
성별 49   초성 33   중성 13   이름공개 8   종성 7   반 4
```

성별이 압도적인데 **광고로 무료로 열 수 있어서**일 가능성이 크다. 순수 선호인지
가격 때문인지 이 데이터로는 못 가른다.

**하트 경제 (여기가 눈에 띈다)**

| 유형 | 건수 | 합계 |
|---|---|---|
| 투표 보상 | 1,174 | **+11,544** |
| 가입 지급 | 23 | +6,900 |
| 충전(스텁) | 6 | **+24,000** |
| 힌트 구매 | 110 | **−16,440** |
| 답장 | 2 | −40 |
| 운영 조정 | 1 | +1,000 |

**들어온 것 43,444 · 나간 것 16,480 → 순증 약 27,000.** 하트가 남아돈다.
다만 충전 24,000 은 **MVP 스텁(무료)** 이라 실제 매출이 아니고, 힌트 110건에는
값이 10배 비쌌던 옛 요금제 구매가 섞여 있다. **지금 값으로 다시 계산해야
의미가 있다** — 이것이 Q3 이 필요한 이유다.

## 4. 【결정 2】 규모 — 얼마나 만들 것인가

### 4-1. 유저 수

| | |
|---|---|
| 지금 설정 | `users.count: 5000` |
| 근거 | 없음(우리가 정한 값) |
| 영향 | 총 행 수가 거의 선형으로 따라간다. 5,000명 → 약 786만 행 |

**내 추천: 5,000명 유지.**

- 786만 행은 **생성 25초 · 로컬 적재 89초 · BigQuery 450MB** 였다. 전부 무료
  한도 안이고, 파라미터를 고쳐 다시 돌리는 데 부담이 없다.
- 더 줄이면(예: 1,000명) 학교당 밀도가 낮아져 친구 그래프가 성립하지 않는다.
- 더 늘리면(예: 50,000명) BigQuery 무료 한도(10GiB)는 견디지만 **반복 실행이
  괴로워진다.** 1차에서는 빨리 도는 게 중요하다.

> ✍️ **정할 것:** 유저 수 ______

### 4-2. 기간

| | |
|---|---|
| 지금 설정 | `months: 3`, `start_date: 2026-04-01` |
| 근거 | 없음 |
| 영향 | **리텐션 분석의 상한을 정한다.** 3개월이면 90일 이상 잔존은 관측 불가 |

**내 추천: Q1(왜 떠나는가)을 고르면 6개월, 아니면 3개월.**

- 리텐션 구간이 `long_term: 30일+` 으로 잡혀 있다. 3개월이면 이 구간의 유저가
  **최대 60일까지만** 관측된다. "3개월 잔존율"을 말하려면 3개월치로는 부족하다.
- 6개월로 늘리면 행 수가 약 2배가 되는데, 그래도 1,500만 행 수준이라 감당된다.
- **끝 날짜를 오늘 근처로 잡을 것.** 지금 `2026-04-01 + 3개월 = 6월 30일`인데
  오늘이 7월 31일이다. 한 달 비는 것이 분석에서 어색하다.

> ✍️ **정할 것:** 기간 ______ 개월 / 시작일 ______

### 4-3. 학교 수와 밀도 ★ 여기가 가장 미묘하다

| | |
|---|---|
| 지금 설정 | `schools.count: 300`, 학교당 학급 9~18, 학급당 14~22명 |
| 근거 | 구 서비스 실측(학급 평균 15개, 같은 반 16.5명) |
| 영향 | **친구 그래프 · CLASS 스코프 투표 · 후보 부족(padded_count) 전부** |

주의 사항이 설정 파일에 이미 적혀 있다:

> 5,000명을 300개 학교에 고루 뿌리면 학급당 1.2명이 되어 "같은 반 친구"를 뽑을
> 풀 자체가 사라진다. 실제 서비스도 5,951개 학교 중 **단 10곳에만** 활동이 몰렸다.

**정해야 할 것은 "몇 개 학교에 몰 것인가"다.** 지금은 코드가 알아서 일부 학교만
채우는데, **그 비율이 설정으로 노출돼 있지 않다.**

**내 추천: 노출시키고 "활동 학교 15~25곳"으로 잡는다.**

- 유저 5,000명 ÷ 20개교 = 학교당 250명 → 학급 15개 기준 학급당 약 17명.
  구 서비스 실측(16.5명)과 맞는다.
- 학교가 너무 적으면(5곳) SCHOOL 스코프가 GLOBAL 과 구별되지 않는다.
- 너무 많으면(100곳) CLASS 스코프에서 후보가 계속 모자라 `padded_count` 가
  치솟는다 — 그 자체가 관측 대상이긴 하지만 1차에서는 잡음이다.

> ✍️ **정할 것:** 학교 마스터 ______ 개 / 활동 학교 ______ 개

### 4-4. 예상 산출물 (참고)

5,000명 · 3개월 기준 실측이었다:

```
총 786만 행 · 로컬 Postgres 476MB · BigQuery 450MB
가장 큰 표: vote_candidate 379만 · heart_transaction 175만 · vote_item 80만

```

기간을 6개월로 늘리면 대략 **2배**로 보면 된다.

## 5. 【결정 3】 추이 — 시간에 따라 어떻게 움직일 것인가

규모보다 이쪽이 분석의 질을 정한다. **"평평한 3개월"은 아무것도 안 알려준다.**

### 5-1. 가입 곡선

| | |
|---|---|
| 지금 설정 | `signup_spike_ratio: 0.6` — 60%가 첫 2주에 가입 |
| 근거 | 구 서비스 실측(2023-05 한 달에 전체의 **93.9%**) |
| 영향 | 코호트 분석이 가능한지 여부 |

**내 추천: 0.6 유지, 다만 "왜 0.6인가"를 기록해 둘 것.**

93.9% 를 그대로 쓰면 **코호트가 사실상 하나**가 되어 "언제 가입한 사람이 더
오래 남나"를 못 본다. 완화한 것은 합리적인데, 그게 **분석 편의를 위한 왜곡**임을
명시해야 한다. 이 값은 실제 서비스를 예측하는 값이 아니다.

## 6. 【결정 4】 기능별 파라미터 — 새로 정해야 하는 것들

3장의 **갈래 C(근거 없음)** 에 해당하는 것들이다. 여기가 실제 토론거리다.

### 6-1. 선택형 힌트 ★ 가장 중요

W14 에서 순차 4단계를 버리고 선택형 5+1 로 바꿨다. 생성기는 **아직 옛 모델**이다.

정해야 할 것 —

| 항목 | 물음 | 내 추천 |
|---|---|---|
| 구매율 | 받은 투표 중 몇 %에서 힌트를 사나 | 실유저 8.7% → **10%** |
| 종류 선호 | 5종 중 무엇을 먼저 사나 | 실유저 비율을 쓰되 **성별 편중은 완화** |
| 몇 개까지 | 산 사람은 평균 몇 개 사나 | **1.8개** (3개 이상 열어야 이름이 열리는 구조를 반영) |
| 이름 공개 | 3개 이상 연 사람 중 몇 %가 100하트를 쓰나 | **35%** |
| 광고 무료 | 성별 힌트 중 광고로 연 비율 | **40%** (1일 1회 제한이 있어 상한이 있다) |

**성별 편중을 완화하자는 이유** — 실유저 데이터에서 성별이 49건으로 압도적인데,
이게 **선호 때문인지 무료라서인지 구분이 안 된다.** 그대로 쓰면 "성별이 제일
궁금하다"는 결론이 데이터에 미리 심겨 들어간다. 그건 발견이 아니라 순환논법이다.

> ✍️ **정할 것:** 위 다섯 값 ______

### 6-2. 하트 경제 — 스텁 충전을 어떻게 다룰 것인가

**결정이 필요한 지점이 명확하다.** MVP 의 충전은 **결제 없는 스텁**이고 하루 한
번 무료다. 합성 데이터에서 이걸 —

- **(가) 스텁 그대로** 재현: 무료·1일 1회. 현실의 우리 서비스와 같다
- **(나) 실제 결제**로 재현: 구 서비스 실측(전환율 8.7%, 1인당 1.6회)

**내 추천: (나) 실제 결제.** 이유는 —

- 스텁을 재현하면 **하트가 무한정 공급**되어 Q3(하트 경제가 성립하는가)의 답이
  "언제나 성립한다"로 고정된다. 물어볼 가치가 없어진다.
- 구 서비스 실측치가 있으므로 근거도 있다.
- 대신 **실유저 데이터와 합성 데이터의 충전 모델이 다르다**는 것을 명시하고,
  실유저 쪽은 `store_transaction_id` 의 `MVP-STUB-` 접두어로 걸러낸다.

⚠️ **어느 쪽이든 힌트 요금을 새 값(20/100)으로 고친 뒤에 계산해야 한다.**
옛 요금(200~1000)으로는 하트가 부족해지고, 새 요금으로는 남아돈다. **요금을
바꾼 것이 하트 경제를 어떻게 바꿨는지가 Q3 의 핵심 질문**이 될 수 있다.

> ✍️ **정할 것:** (가) / (나) ______

## 9. 작업 순서 (결정 후)

한 번에 다 하지 말고 **한 바퀴를 먼저 완주**한다.

1. **파라미터 확정** — 위 표를 채운다. `distribution.yaml` 에 반영
2. **생성기 수정** — 최소한 힌트 모델(11·12번). 여기가 가장 큰 작업
3. **작게 먼저** — `users.count: 200` 으로 한 번 돌려 생성기가 안 깨지는지 확인
4. **정합성 검사** — 로컬 적재 후 `qa/checks/integrity.sql` 17종 위반 0
5. **전량 생성** — 확정 규모로 다시
6. **BigQuery 적재** — `extract_load.py --source local --full-refresh`
7. **행 수 대조** — `verify_load.py --source local`
8. **분석 한 바퀴** — 1장에서 고른 질문에 실제로 답해본다
9. **되돌아보기** — 답이 안 나오는 질문이 있으면 그게 2차 파라미터 조정 대상

**3번(작게 먼저)을 건너뛰지 말 것.** 생성기가 스키마와 어긋난 곳이 아직 있을 수
있고, 5,000명으로 25초 돌린 뒤 실패하는 것보다 200명으로 1초 만에 실패하는 게 낫다.

## 10. 이 문서를 쓰면서 발견한 것

기록해 둔다. 팀 논의에서 다시 나올 내용이다.

1. **생성기가 오류 없이 틀린 데이터를 만든다.** 힌트 요금이 10배 다른데 스키마가
   맞아서 그냥 들어간다. 이 프로젝트가 반복해서 물린 "조용한 실패"의 또 다른 형태다.
2. **`char_index` 가 NULL 이면 자모 힌트가 화면에서 안 보인다.** W14 에서 실유저
   19건이 실제로 그랬다. 생성기도 같은 상태다.
3. **활동 학교 수가 코드에 숨어 있다.** 친구 그래프의 성립 여부를 좌우하는 값인데
   설정으로 못 바꾼다.
4. **우리 실유저는 이탈 모델링에 못 쓴다.** 탈퇴 0명, 친구 끊기 0건이다.
   지인이라 안 나간다 — 이건 표본이 작아서가 아니라 **표본의 성격 문제**다.
