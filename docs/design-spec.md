# 데이터 파이프라인 에이전트 시스템 설계서

**작업명**: 학교 기반 소셜 투표 서비스의 데이터 파이프라인 구축 및 운영 자동화

이 문서는 Claude Code에서 구현할 때 참조하는 **계획서**다. 구현 상세(코드, 스키마 정의)는 여기 적지 않는다.
프로젝트 요약은 [[CLAUDE]], 결정 이력은 [[DECISIONS]] 참조.

---

# 1. 작업 컨텍스트

## 1.1 배경

기존 학교 소셜 투표 서비스의 DB(`final` / `hackle` 스키마, 가입자 67.7만, 14개월치)를 분석하면서
**분석을 가로막는 구조적 결함**이 반복해서 드러났다.

| 발견 | 결과 |
|---|---|
| 탈퇴 테이블에 유저 식별자 없음 | 이탈 원인 분석 원천 불가 |
| 원장에 충전·가입지급 누락 | 잔액 재구성 불가 (원장 201만 vs 잔액 20억) |
| 관계 39개 중 FK 선언은 17개 | 무결성 깨짐이 조용히 누적 (고아 26건) |
| 투표 완료 이벤트에 `question_id` 없음 | "무엇에 투표했는지" 복원 불가 |
| 로그인 기록 없음 | 리텐션을 친구요청 발신으로 추정해야 했음 |

즉 **데이터를 나중에 분석할 것을 전제하지 않고 설계된 스키마**였다.
이 프로젝트는 그 결함을 닫은 스키마를 새로 만들고, 실제로 돌아가는 적재 파이프라인을 붙인다.

## 1.2 목적

1. 분석 가능성을 전제로 설계된 스키마를 **실제 DB로 구현**한다
2. 합성 데이터와 외부 실데이터를 **Airflow로 BigQuery에 적재**하는 파이프라인을 구축한다
3. 개발 경험이 없는 작업자가 **에이전트의 도움으로 완주**할 수 있는 구조를 만든다

## 1.3 범위

**포함**
- 스키마 DDL 작성 및 Supabase(PostgreSQL) 구축
- 합성 데이터 생성 (유저 5,000명 / 3개월치)
- NEIS 공개 API에서 학교·급식·시간표·학사일정 수집
- Airflow DAG 작성 및 운영 (수집 / 적재 / 검증)
- BigQuery raw → staging → mart 레이어 구성
- 데이터 품질 검증 자동화
- 대시보드 (Looker Studio)

**제외**
- 앱스토어 배포, 인앱결제, 사업자등록
- 익명 게시판 운영 (스키마만 설계, v1 미개통)
- 웹앱 개발 — 별도 트랙이며 이 설계서 범위 밖. 완성 시 같은 파이프라인에 실유저 데이터가 합류한다.

## 1.4 입출력 정의

### 입력

| 입력 | 형태 | 출처 | 갱신 주기 |
|---|---|---|---|
| 스키마 설계 | ERD 설계안 (43 테이블) | 기존 분석 산출물 | 변경 시 |
| 생성 파라미터 | 유저 수, 기간, 분포 명세 | 작업자 지정 | 변경 시 |
| NEIS 데이터 | JSON (REST API) | 교육정보 개방포털 | 일 1회 |
| 실유저 활동 | PostgreSQL 테이블 | Supabase (웹앱 완성 후) | 일 1회 |

### 출력

| 출력 | 형태 | 위치 |
|---|---|---|
| 스키마 정의 | `.sql` DDL | `db/ddl/` |
| 합성 데이터 | `.csv` / DB 적재분 | `data/synthetic/` |
| 적재 결과 | BigQuery 테이블 | `raw_*` / `stg_*` / `mart_*` |
| 품질 리포트 | `.md` | `reports/qa/YYYY-MM-DD.md` |
| 실행 로그 | Airflow 태스크 로그 | Airflow UI |

## 1.5 제약조건

| 구분 | 제약 |
|---|---|
| **작업자** | 개발 경험 없음. 코드 작성·디버깅은 전량 에이전트가 수행 |
| **비용** | 월 0~3만원. 무료 티어를 벗어나는 선택지는 채택하지 않음 |
| **인프라** | Airflow는 로컬 Docker. PC가 꺼지면 스케줄이 멈추는 것을 전제로 설계 |
| **데이터 분리** | 실유저 데이터와 합성 데이터를 같은 DB에 섞지 않음 |
| **개인정보** | 성인 지인만. 전화번호 미수집. 이름은 마스킹 저장 |
| **기존 자산** | `mysql` 컨테이너(포트 3307)의 `final`/`hackle`은 읽기만. 변경 금지 |

## 1.6 용어 정의

| 용어 | 의미 |
|---|---|
| **스코프(scope)** | 투표 후보를 뽑는 범위. `CLASS` / `SCHOOL` / `GLOBAL` 세 단계 |
| **아이템(vote_item)** | 유저에게 출제된 질문 1건. 구 스키마의 "질문 피스"에 해당 |
| **세션(vote_session)** | 아이템 여러 개를 묶은 한 번의 투표 회차 |
| **셔플(shuffle)** | 후보 4명이 마음에 안 들 때 1회 한정 재추첨. 광고 시청 필수 |
| **하트** | 유일한 통화. 구 스키마에서 `point`와 `heart`로 이원화돼 있던 것을 통합 |
| **합성 데이터** | 파이프라인 검증용 생성 데이터. 실유저와 구분하기 위해 `is_synthetic=true` |
| **raw / stg / mart** | BigQuery 레이어. 원본 그대로 / 정제·타입 정리 / 분석용 집계 |
| **에스컬레이션** | 에이전트가 자동 처리하지 않고 작업자 판단을 요청하는 것 |

# 2. 워크플로우 정의

## 2.1 전체 흐름

```
[P0] 스키마 확정 ──> DDL 작성 ──> Supabase 구축
                                      │
        ┌─────────────────────────────┴──────────────────────────┐
        ↓                                                        ↓
[P1] 합성 데이터 생성                                  [P3] NEIS 실데이터 수집
        ↓                                                        ↓
[P2] Postgres 적재 ─────────────┬───────────────────────────────┘
                                ↓
                    [P4] BigQuery 적재 (raw)
                                ↓
                    [P5] 데이터 품질 검증 ──[실패]──> 에스컬레이션
                                ↓ [통과]
                    [P6] stg / mart 변환
                                ↓
                    [P7] 대시보드
```

P1과 P3은 서로 의존하지 않으므로 **병렬 진행 가능**하다.
P5는 게이트다 — 통과하지 못하면 P6로 넘어가지 않는다.

## 2.2 단계별 정의

### P0 · 스키마 확정 및 DDL 작성

| 항목 | 내용 |
|---|---|
| 입력 | ERD 설계안 (43 테이블), 미결 사항 목록 |
| 출력 | `db/ddl/*.sql`, Supabase에 생성된 테이블 |
| 성공 기준 | 43개 테이블 생성 · FK 전부 선언 · 빈 DB에서 DDL 재실행 가능 · 업무규칙 제약이 실제 위반을 차단 |
| 검증 방법 | `information_schema` 카운트 대조 + **위반 시나리오를 실제로 INSERT 해서 거부되는지 확인** |
| 실패 처리 | DDL 오류 → 즉시 수정 후 재실행. 설계 자체의 모순(순환 FK 등) → **에스컬레이션** |

**완료 (2026-07-29)** — 43 테이블 / FK 77 / UNIQUE 26 / CHECK 12 / ENUM 29.
순환 FK 3쌍을 단방향으로 정리(→ [[DECISIONS]]). 위반 시나리오 16종 전부 차단 확인.

> 카운트만 세는 검증으로는 부족하다. 제약이 **선언되어 있는 것**과 **실제로 막는 것**은 다르므로,
> 셔플 2회·광고 없는 셔플·자기 자신 지목·급식 중복 같은 위반을 직접 INSERT 해서 거부를 확인했다.

### P1 · 합성 데이터 생성

| 항목 | 내용 |
|---|---|
| 입력 | 스키마, 생성 파라미터(유저 5,000 / 3개월) |
| 출력 | `data/synthetic/*.csv` |
| 성공 기준 | 모든 FK가 유효 · 유저당 친구 수 5명 이상(게이트 조건) · 시간 순서 모순 없음(투표가 가입보다 앞서지 않음) |
| 검증 방법 | 생성 직후 정합성 스크립트 실행 + **분포의 현실성을 LLM이 판단** |
| 실패 처리 | FK 위반 → 생성 로직 수정 후 재생성. 분포가 비현실적 → LLM이 파라미터 조정 제안 |

**LLM 판단 필요 — 이 단계의 핵심.** 기계적 검증(FK, NOT NULL)은 스크립트가 하지만,
**"이 데이터가 그럴듯한가"** 는 판단 영역이다. 구체적으로:

- 리텐션 곡선이 현실적인가 (기존 서비스는 1주 내 이탈 63.9%였다 — 너무 매끄러운 곡선은 가짜 티가 난다)
- 투표 참여가 소수에 쏠려 있는가 (기존은 0.7% 파워유저 편중)
- 친구 그래프가 학교·반 구조를 반영하는가 (기존은 같은 학교 친구 79.6%)
- 하트 잔액과 거래 원장이 일치하는가

### P2 · Postgres 적재

| 항목 | 내용 |
|---|---|
| 입력 | 합성 CSV |
| 출력 | Supabase(또는 별도 합성용 DB)에 적재된 데이터 |
| 성공 기준 | 적재 행 수 = 생성 행 수 · FK 위반 0건 · **시퀀스 재동기화 완료** |
| 검증 방법 | 테이블별 행 수 대조 쿼리 + 자동 id 발급 테스트 |
| 실패 처리 | 부분 실패 → 해당 테이블만 truncate 후 재적재. 전체 실패 → **에스컬레이션** |

> **필수 후처리**: 적재 직후 `db/ddl/95_resync_sequences.sql` 실행.
> identity 컬럼에 id를 직접 지정하면 시퀀스가 전진하지 않아, 이후 실유저 가입이
> id=1을 발급하려다 PK 충돌로 실패한다. P0 검증 중 실제로 재현된 문제다.

### P3 · NEIS 실데이터 수집

| 항목 | 내용 |
|---|---|
| 입력 | NEIS API 키, 대상 학교 목록, 조회 기간 |
| 출력 | `raw_neis_*` 테이블 |
| 성공 기준 | 대상 학교의 90% 이상 응답 수신 · 스키마 파싱 성공 |
| 검증 방법 | 요청 수 대비 성공 수, 필수 필드 결측률 |
| 실패 처리 | 아래 2.4의 분기표 참조 |

### P4 · BigQuery 적재

| 항목 | 내용 |
|---|---|
| 입력 | Postgres 테이블, NEIS raw |
| 출력 | BigQuery `raw_*` 데이터셋 |
| 성공 기준 | 소스 행 수 = 타겟 행 수 · 적재 시각 기록됨 · `is_synthetic` 플래그 정확 |
| 검증 방법 | 소스/타겟 카운트 비교, 파티션별 행 수 |
| 실패 처리 | 재시도 3회 → 실패 시 **에스컬레이션**. 부분 적재분은 파티션 단위로 삭제 후 재적재(멱등성 보장) |

### P5 · 데이터 품질 검증 — **게이트**

| 항목 | 내용 |
|---|---|
| 입력 | BigQuery raw 테이블 |
| 출력 | `reports/qa/YYYY-MM-DD.md` |
| 성공 기준 | 아래 검사 전부 통과 |
| 실패 처리 | 심각도에 따라 분기 (2.4 참조) |

검사 항목:

| 검사 | 기준 | 심각도 |
|---|---|---|
| 참조 무결성 | 고아 행 0건 | **높음** — 즉시 중단 |
| 하트 원장 정합성 | `balance_after` 최종값 = `user.heart_balance` | **높음** |
| 행 수 급변 | 전일 대비 ±50% 이내 | 중간 — 확인 요청 |
| 필수 필드 결측 | NOT NULL 컬럼에 결측 0건 | **높음** |
| 시간 순서 | 활동 시각 > 가입 시각 | 중간 |
| 중복 | UNIQUE 제약 대상 중복 0건 | **높음** |
| 급식 데이터 공백 | 주말·방학 제외하고 결측 | 낮음 — 로그만 |

**LLM 판단 필요**: 행 수 급변이 **버그인지 정상 변동인지** 구분한다.
예 — 학기 시작으로 급식 데이터가 늘어난 것은 정상이고, 유저 수가 그대로인데 투표가 3배가 된 것은 의심스럽다.
숫자만으로는 갈리지 않으므로 맥락 판단이 필요하다.

### P6 · stg / mart 변환

| 항목 | 내용 |
|---|---|
| 입력 | raw 테이블 |
| 출력 | `stg_*`, `mart_*` |
| 성공 기준 | 변환 전후 키 개수 보존 · 집계값이 raw 재계산과 일치 |
| 실패 처리 | 변환 SQL 오류 → 수정 후 재실행 |

주요 마트: 일별 활성 유저, 코호트 잔존율, 투표 퍼널, 하트 수급, 셔플·광고 전환.

### P7 · 대시보드

Looker Studio를 BigQuery mart에 연결. 코드 산출물 없음.

## 2.3 LLM 판단 영역 vs 코드 처리 영역

이 구분이 이 시스템의 핵심 설계다. **결정론적이고 반복되는 것은 코드**, **맥락과 판단이 필요한 것은 LLM**.

### 코드가 처리 (에이전트가 개입하지 않음)

| 작업 | 이유 |
|---|---|
| DDL 실행 | 결정론적 |
| 합성 데이터 생성 (규칙 적용) | 규칙이 정해지면 기계적 |
| API 호출·페이지네이션·재시도 | 정해진 절차 |
| DB → GCS → BigQuery 적재 | 정해진 절차 |
| 정합성 검사 쿼리 실행 | 기준이 명확 |
| 스케줄링 | Airflow 담당 |

### LLM이 판단 (에이전트가 직접 수행)

| 판단 지점 | 무엇을 판단하나 | 왜 코드로 안 되나 |
|---|---|---|
| **스키마 변경 필요성** | 새 요구사항에 컬럼 추가가 맞는지, 테이블 분리가 맞는지 | 설계 트레이드오프 판단 |
| **합성 데이터 현실성** | 분포가 그럴듯한지, 파라미터를 어떻게 조정할지 | "그럴듯함"에 고정 기준이 없음 |
| **품질 이상의 성격** | 행 수 급변이 버그인지 정상 변동인지 | 맥락(학기, 이벤트, 웹앱 배포)을 알아야 함 |
| **실패 처리 경로** | 재시도할지, 스킵할지, 사람을 부를지 | 원인에 따라 다름 |
| **에스컬레이션 판단** | 작업자에게 물어야 하는 사안인지 | 사안의 중대성 평가 |
| **미결 이슈 정리** | 무엇을 물어야 하고 선택지가 무엇인지 | 문제 정의 자체가 판단 |

### 경계에 있는 것 — LLM이 규칙을 만들고 코드가 집행

| 작업 | 분담 |
|---|---|
| 품질 검사 임계값 | LLM이 임계값을 정하고 → 코드가 매일 검사 |
| 합성 데이터 분포 | LLM이 분포 파라미터를 정하고 → 코드가 생성 |
| DAG 구조 | LLM이 태스크 의존성을 설계하고 → Airflow가 실행 |

**원칙**: LLM이 매번 같은 판단을 반복하고 있다면, 그건 규칙으로 굳혀 코드로 내려야 한다는 신호다.

## 2.4 실패 처리 분기

| 상황 | 처리 | 근거 |
|---|---|---|
| NEIS API 타임아웃 / 5xx | **재시도** 3회, 지수 백오프 | 일시적 장애 |
| NEIS API 4xx (키 만료, 잘못된 파라미터) | **에스컬레이션** | 재시도해도 안 됨 |
| 특정 학교·날짜에 급식 없음 | **스킵**, 로그만 | 주말·방학은 정상 |
| BigQuery 적재 부분 실패 | 파티션 삭제 후 **재시도** 3회 → **에스컬레이션** | 멱등성 보장됨 |
| FK 위반 발견 | **즉시 중단 + 에스컬레이션** | 데이터 신뢰성 붕괴, 하류로 전파 금지 |
| 하트 원장 불일치 | **즉시 중단 + 에스컬레이션** | 구 시스템의 가장 큰 결함이 재발한 것 |
| 행 수 ±50% 초과 변동 | **LLM 판단** → 정상이면 통과, 의심되면 에스컬레이션 | 맥락 의존 |
| 스키마 드리프트 (소스에 컬럼 추가/삭제) | **중단 + 에스컬레이션** | 조용히 넘기면 나중에 발견 |
| 합성 데이터 생성 중 제약 위반 | 로직 수정 후 **전량 재생성** | 부분 수정은 정합성이 더 깨짐 |

**에스컬레이션 형식** — 작업자에게 다음을 함께 제시한다:
무슨 일이 있었는가 / 왜 자동 처리하지 않았는가 / 선택지와 각각의 결과 / 권장안.

## 2.5 상태 전이

각 DAG 실행은 다음 상태를 가진다.

```
PENDING ──> RUNNING ──> VALIDATING ──┬──> SUCCESS
                │                    │
                │                    └──> QA_FAILED ──> ESCALATED
                │
                └──> FAILED ──> RETRYING ──> (RUNNING | ESCALATED)
```

- `VALIDATING`을 통과하지 못하면 **하류 태스크는 실행되지 않는다** (Airflow `trigger_rule` 활용)
- `ESCALATED`는 사람이 해제하기 전까지 유지된다. 자동 복구하지 않는다.

## 3.3 에이전트 구조

**메인 에이전트 1 + 서브에이전트 3** 구성.

메인 에이전트가 전 과정을 주관하고, 다음 세 경우에만 서브에이전트에 위임한다:
(1) 컨텍스트를 많이 먹는 작업, (2) 독립적으로 끝나고 요약만 돌려주면 되는 작업, (3) 반복 실행되는 검증.

> 서브에이전트를 늘리지 않는다. 1인 프로젝트에서 에이전트가 많아지면 관리 비용이 이득을 넘는다.

### 단계별 처리 주체

| 단계 | 주체 | 방식 |
|---|---|---|
| P0 스키마·DDL | 메인 에이전트 | 직접 작성 (설계 판단이 핵심) |
| P1 합성 데이터 | `data-generator` 서브에이전트 | 스크립트 작성 위임 → 메인이 분포 검토 |
| P2 Postgres 적재 | 스크립트 | 에이전트 개입 없음 |
| P3 NEIS 수집 | `pipeline-builder` 서브에이전트 | DAG 작성 위임 |
| P4 BigQuery 적재 | `pipeline-builder` 서브에이전트 | DAG 작성 위임 |
| P5 품질 검증 | `data-qa` 서브에이전트 | 검사 실행 → 메인이 이상 여부 판단 |
| P6 stg/mart | 메인 에이전트 | SQL 직접 작성 (분석 설계가 핵심) |
| P7 대시보드 | 작업자 | Looker Studio 수동 구성 |

## 3.4 서브에이전트 정의

### `data-generator`

| 항목 | 내용 |
|---|---|
| **역할** | 합성 데이터 생성 스크립트 작성·수정 |
| **입력** | 스키마 DDL 경로, 생성 파라미터(유저 수·기간·분포 명세) |
| **출력** | 생성 스크립트 파일 경로 + 생성 결과 요약(테이블별 행 수, 제약 검사 결과) |
| **데이터 전달** | 파일 경로로 주고받는다. 생성된 데이터 자체를 대화로 넘기지 않는다 |
| **위임 이유** | 43개 테이블의 관계 정합성을 지키는 생성 순서·로직이 길다. 메인 컨텍스트를 소모시키지 않는다 |
| **위임하지 않는 것** | 분포가 현실적인지 **판단**은 메인이 한다. 서브는 만들기만 한다 |

### `pipeline-builder`

| 항목 | 내용 |
|---|---|
| **역할** | Airflow DAG 작성 및 수정 |
| **입력** | 소스·타겟 명세, 스케줄, 재시도 정책, 멱등성 요구사항 |
| **출력** | DAG 파일 경로 + 태스크 구조 요약 + 로컬 파싱 검증 결과 |
| **데이터 전달** | 파일 경로. DAG 실행 로그는 요약만 반환 |
| **위임 이유** | DAG 보일러플레이트가 길고 반복적이다 |
| **위임하지 않는 것** | 태스크 의존성 **설계**와 실패 처리 정책 결정은 메인이 한다 |

### `data-qa`

| 항목 | 내용 |
|---|---|
| **역할** | 적재 후 품질 검사 실행 및 이상 항목 수집 |
| **입력** | 검사 대상 테이블 목록, 검사 정의(`qa/checks/`), 비교 기준일 |
| **출력** | 이상 항목 리스트(항목·심각도·실측값·기준값) + 리포트 파일 경로 |
| **데이터 전달** | 리포트는 `qa/reports/YYYY-MM-DD.md`로 쓰고 경로만 반환. 쿼리 결과 원본은 넘기지 않는다 |
| **위임 이유** | 검사 쿼리를 여러 개 돌리면 출력이 길다. 요약만 필요하다 |
| **위임하지 않는 것** | 이상이 **진짜 문제인지 판단**과 에스컬레이션 여부는 메인이 결정한다 |
