# P5~P7 시작하기

EDA(AARRR)까지 끝난 상태에서 **다음 네 가지를 어떤 순서로, 어떤 명령으로**
시작하는지 적는다. 각 단계마다 "무엇을 하는가 · 명령 · 끝났다의 기준"이 있다.

> 명령은 전부 `.venv` 로 돈다. 활성화해 뒀다면 `python`, 아니면
> `.venv\Scripts\python.exe` (Git Bash 는 `./.venv/Scripts/python.exe`).

---

## 왜 이 순서인가

층이 넷이고, **앞이 틀리면 뒤는 전부 틀린다.** 그런데 뒤로 갈수록
틀린 것이 안 보인다 — 대시보드는 숫자가 틀려도 예쁘게 나온다.

| 층 | 무엇 | 형태 | 누가 읽나 |
|---|---|---|---|
| **raw** | 원본 그대로. 제약도 정리도 없다 | 테이블(파티션) | 파이프라인만 |
| **stg** | 실수를 구조적으로 막은 층 | **뷰** (저장 0) | mart 와 분석자 |
| **mart** | 지표를 미리 계산해 둔 표 | **테이블** (작다) | 대시보드 |
| **대시보드** | 그림 | 루커 스튜디오 | 사람 |

그래서 **P5(raw 를 믿을 수 있나) → stg(정리) → mart(지표) → 대시보드** 다.

## P5 · 품질검증 — `qa/quality_check.py`

### 무엇을 하는가

`verify_load.py` 와 헷갈리기 쉬운데 **묻는 것이 다르다.**

| | 묻는 것 |
|---|---|
| `verify_load.py` | 원천의 행이 **다 왔나** (개수 대조) |
| `quality_check.py` | 온 행을 **믿어도 되나** (내용 검증) |

raw 층은 일부러 제약이 없다. 적재기가 모든 컬럼을 NULLABLE 로 만들고 외래키도
걸지 않는다 — 원천 스키마가 느슨해질 때 적재가 통째로 죽지 않게 하려는 선택이다.
**그래서 검증이 적재 시점이 아니라 여기에 있다.**

검사는 손으로 적지 않는다. `docs/erd.json`(살아 있는 스키마)을 읽어 표마다
자동으로 만든다 — 표가 늘면 검사도 는다. **지금 430개.**

| 구분 | 보는 것 | 개수 |
|---|---|---|
| 유일성 | `(_source, id)` 가 중복되지 않는가 | 40 |
| 필수값 | 원천이 NOT NULL 인 컬럼에 NULL 이 없는가 | 276 |
| 참조 | 부모 없는 자식 행이 없는가 (**같은 `_source` 안에서만**) | 75 |
| 시각 | 미래 시각 · 뒤집힌 순서(`voted_at < served_at` 등) | 39 |
| 적재 상태 | 워터마크가 언제 것인가 (정보) | — |

### 명령

먼저 **얼마나 스캔하는지만** 본다. 쿼리 무료 한도가 월 1 TiB 뿐이라
비용을 모르고 켜지 않는다.

```
python qa/quality_check.py --source supabase --estimate
```

숫자를 보고 괜찮으면 실제로 돌린다.

```
python qa/quality_check.py --source supabase
```

합성 데이터도 같은 방법으로 본다 (`--source local`).

### 끝났다의 기준

- 네 구분 전부 `✅`, 위반 0
- 리포트가 `qa/reports/quality-<날짜>-<원천>.md` 로 남고, 그것을 커밋했다

**실측 (2026-08-18)** — 두 원천 다 **430/430 통과**. 한 번에 11.7 GiB 를
스캔한다(월 무료 한도의 1.1%). 매일 돌려도 한 달 34% 다.

### 언제 다시 도나

- 적재를 돌린 뒤
- **스키마를 바꾼 뒤** — 컬럼을 추가하면 `updated_at` 이 안 움직여 증분이
  못 잡는다. 그 컬럼이 통째로 NULL 로 남고, "필수값" 검사가 그것을 잡는다

## P6-1 · 스테이징 — `bigquery/build.py --layer stg`

### 무엇을 하는가

**raw 를 그대로 쓰지 못하게 만드는 층**이다. 분석에서 실제로 걸렸던 실수 넷을
사람의 기억이 아니라 **컬럼으로** 막는다.

| 막는 실수 | 어떻게 |
|---|---|
| 두 원천의 id 가 겹친다 (`app_user` 16개) | `user_key = 'local-123'` 같은 **대리키**. `USING(id)` 를 못 쓰게 된다 |
| 지운 행의 유령 | `_deleted_at IS NULL` 을 뷰 안에서 한 번만 건다 |
| 시간대가 9시간 밀린다 | `signup_date` 처럼 **KST 날짜를 미리 계산**해 싣는다 |
| 광고 무료 힌트가 '구매'로 세어진다 | `is_paid_hint` · `is_ad_hint` 로 갈라 둔다 |
| 스텁 충전이 매출로 세어진다 | `is_stub` · `is_revenue` 로 갈라 둔다 |
| 제재 유저를 유저 단위로 빼면 과거까지 사라진다 | `valid_until` **시각**을 싣는다 |

### 왜 테이블이 아니라 뷰인가

raw 가 이미 8.74 GiB 라 **무료 저장 한도 10 GiB 의 여유가 1 GiB 남짓**이다.
stg 를 테이블로 구우면 그 여유가 사라진다. 뷰는 저장이 0이고, 읽는 쪽이
mart 와 분석자뿐이라 재조회 비용도 작다.

거꾸로 **mart 는 테이블이어야 한다.** 대시보드는 화면을 그릴 때마다 쿼리를
날리는데, 뷰로 두면 그때마다 1억 2천만 행을 다시 읽는다.

### 명령

문법과 스캔량만 먼저 본다.

```
python bigquery/build.py --layer stg --dry-run
```

괜찮으면 만든다. (`stg` 데이터셋이 없으면 자동으로 만든다.)

```
python bigquery/build.py --layer stg
```

### 지금 있는 것 (2026-08-18 생성 완료)

| 뷰 | 한 행이 뜻하는 것 |
|---|---|
| `stg.stg_user` | 유저 한 명 (+ 소속 · **지역(시도)** · 탈퇴 · 제재 · `valid_until`) |
| `stg.stg_user_session` | 접속 세션 한 건 (+ 체류시간 · 중복 표시) |
| `stg.stg_vote_session` | 투표 세션 한 건 (+ 완료 여부) |
| `stg.stg_vote_item` | 출제된 질문 한 건 (+ 질문 마스터 · 응답 소요) |
| `stg.stg_vote_received` | **받은 투표 한 건** (+ 열람 · 공개 단계) |
| `stg.stg_hint_purchase` | 힌트를 연 기록 한 건 (+ 유료/광고 구분) |
| `stg.stg_heart_transaction` | 하트 원장 한 줄 (+ 적립/소비 분리) |
| `stg.stg_heart_purchase` | 충전 시도 한 건 (+ 스텁/매출 구분) |
| `stg.stg_friend_edge` | **친구 관계를 유저 관점으로 편 것** (관계 1건 = 두 행) |
| `stg.stg_report` | **신고 한 건** (+ 사유 라벨 · 처리 여부) |

뒤의 넷과 `stg_user` 의 지역은 **대시보드 때문에 늘었다** — 스케치 5쪽 중
2·3·5쪽이 기존 6개로는 그려지지 않았다([[stg-views-for-dashboard]]).

**SQL 은 `bigquery/staging/*.sql` 이 진실이다.** 파일 이름의 번호가 실행 순서다.

### 끝났다의 기준

- `--dry-run` 없이 10개 파일이 전부 `생성` 으로 끝났다
- `stg_friend_edge` 의 행 수가 `friendship` 의 **정확히 2배**다
  (실측 795,656 = 397,828 × 2). 양방향으로 폈다는 뜻이고, 안 맞으면 한쪽만 센 것이다
- `stg_user.sido` 에 NULL 이 없다 (실측 0건 · 합성은 10개 시도)

## P6-2 · 마트 (2026-08-18 생성 완료 · 표 8개)

지표는 `notebooks/dashboard.ipynb` 의 12개에서 출발했지만, **그레인을 정한 것은
대시보드의 기간 필터**다. "주 단위로 좁혀 전주와 비교한다"가 붙는 순간
월 그레인·사전 계산된 비율·미리 센 distinct 가 전부 못 쓰게 된다
([[mart-grain-for-weekly-filter]]).

### 주간 규칙 넷 — 마트를 쓸 때 이걸 먼저 본다

| 규칙 | 어기면 |
|---|---|
| ① 모든 표에 날짜 컬럼(`metric_date`) | 루커의 '비교 기간(전주)'이 아예 안 켜진다 |
| ② **비율을 굽지 않는다.** 분자·분모를 싣는다 | 주간 비율이 "일별 비율의 평균"이 된다 |
| ③ **distinct 를 사전 집계하지 않는다** | 월 표에서 주간 MAU 를 못 낸다. DAU 를 7일 더해도 WAU 가 아니다 |
| ④ 퍼널·분포는 **사건일 또는 코호트일**로 자른다 | 기간을 좁힐 때 같은 대상이 두 주에 중복된다 |

여기에 층의 규칙 넷이 그대로 얹힌다 — **raw 를 직접 읽지 않는다**(항상 `stg`) ·
**대리키로 잇는다** · **걸러서 담는다**(운영자 제외 · `valid_until` 이후 제외 ·
중복 세션 제외) · 날짜로 `PARTITION`, 원천으로 `CLUSTER`.
⚠️ 단 **차원 표(유저)는 걸러 담지 않는다** — 탈퇴자를 지우면 이탈률의 분자가 사라진다.

### 표 여덟 개

| 표 | 그레인 | 행 · 크기 | 어느 화면 |
|---|---|---|---|
| `mart_user` | 유저 1명 (축=가입일) | 2.0만 · 6 MiB | 1쪽 KPI · 2쪽 전부 |
| `mart_user_activity` | **유저 × 활동일** | 229만 · 384 MiB | MAU·WAU·주간 투표자/결제자 |
| `mart_daily` | 일자 × 차원 (**합계 전용**) | 3.4만 · 6 MiB | 시계열 |
| `mart_funnel_step` | 퍼널 × 단계 × 차원 | 27만 · 29 MiB | 1쪽·3쪽 퍼널 |
| `mart_distribution` | 분포 × 버킷 × 차원 | 40만 · 42 MiB | 3쪽 분포 셋 |
| `mart_report` | 신고 1건 | 3.1만 · 4 MiB | 5쪽 전부 |
| `mart_heart_flow` | 일자 × 하트 유형 × 차원 | 20만 · 24 MiB | 4쪽 유입·소비처 |
| `mart_backlog_weekly` | **주 스냅샷** | 3천 · 0.3 MiB | 적체의 전주 대비 |

합쳐서 **약 495 MiB**다. 저장 무료 한도(10 GiB) 여유 안에 들어간다.

차원은 여덟 표가 **같은 이름**을 쓴다 — `source`·`sido`·`school_type`·`grade`·`gender`.
루커의 보고서 수준 필터가 한 번에 걸리려면 이름이 같아야 한다.

⚠️ **`mart_user_activity` 가 이 설계의 핵심이다.** 사람 수를 세는 일은 전부 여기서
한다. `mart_daily` 에는 활성 유저 수가 **일부러 없다** — 사람 수는 날짜 축으로
더해지지 않기 때문이다(규칙 ③).

⚠️ **`mart_funnel_step` 의 `user_journey` 는 단조 감소하지 않는다.** 단계가 독립
플래그라 "투표 세션 완료 13,873 → 1단계 힌트 15,210"처럼 다시 늘어난다.
힌트는 받은 투표에서 사는 것이라 투표 세션과 인과가 없다 — **퍼널 도형이 아니라
막대 묶음으로 그린다.** `vote_received` 퍼널은 수신 건 하나를 따라가므로 단조 감소가 맞다.

### 명령

```
python bigquery/build.py --layer mart --dry-run
python bigquery/build.py --layer mart
```

⚠️ **`--dry-run` 은 빈 데이터셋에서 40번부터 실패한다.** `mart_funnel_step` 이
`mart_user` 를 읽는데 dry-run 은 표를 만들지 않기 때문이다. 처음 만들 때는
`--dry-run` 없이 돌린다 — 번호 순서라 10번이 먼저 만들어진다.

⚠️ **일일 쿼리 하드캡에 걸릴 수 있다**([[row-cap-to-query-cap]]). 전체 빌드가
**7.3 GiB** 를 스캔한다. `Custom quota exceeded` 가 뜨면 콘솔 →
IAM 및 관리자 → 할당량 → `Query usage per day` 를 올리거나, 태평양 자정
(KST 16:00~17:00)에 리셋되기를 기다린다. 오늘 얼마나 썼는지는
`INFORMATION_SCHEMA.JOBS_BY_PROJECT` 로 본다.

**조금씩 작은 것이 정상이다.** 노트북은 제재(BAN)를 아무 데서도 안 거르지만

## P7 · 루커 스튜디오

코드가 필요 없는 단계다. **파이썬은 여기서 끝난다.**

### 순서

1. https://lookerstudio.google.com 에 **BigQuery 와 같은 구글 계정**으로 들어간다
2. 만들기 → 데이터 원본 → **BigQuery** 커넥터
3. 프로젝트 `ping-v2-503916` → 데이터셋 **`mart`** → 표를 고른다
4. 보고서 만들기 → 차트를 얹는다

### 지도를 그리려면 — `sido` 가 아니라 `sido_iso` 를 쓴다

루커 스튜디오의 지도는 필드 **타입이 `지역`/`지역 ID`** 여야 그려진다.
그런데 **한글 시도명으로는 매칭이 붙지 않는다** — 특히 `강원특별자치도` 처럼
최근 개편된 이름은 확실히 실패한다. 그래서 마트 여덟 표 전부에
**ISO-3166-2 코드**(`KR-11`·`KR-42` …)를 `sido_iso` 로 함께 싣는다(2026-08-18).

1. 데이터 원본 편집 → `sido_iso` 의 타입을 **지리 > 지역 ID**(Region ID) 로 바꾼다
2. 지도 차트의 측정기준으로 `sido_iso` 를 쓴다. **`sido` 는 라벨·필터용으로 남긴다**

매핑은 `bigquery/staging/10_stg_user.sql` 한 곳에 있다 — stg 에 두었으므로
**마트 여덟 개가 자동으로 물려받는다.** 17개 시도를 전부 적었고 옛 이름
(강원도·전라북도·제주도)도 받는다. ⚠️ **못 알아본 값은 NULL 로 남긴다** —
틀린 코드를 넣으면 엉뚱한 지역이 칠해지고 아무도 눈치채지 못한다.
실측(2026-08-18)으로 NULL 은 **0건**이다.

⚠️ **지도가 뜻을 갖는 것은 합성 데이터뿐이다.** 실유저 23명은 전원 서울이라
사본 대시보드에서는 지도를 빼는 편이 낫다. 그리고 이 지역 값은 학교를 거쳐
붙는 **자기신고**다([[school-boundary-self-reported]]).

### ⚠️ `raw` 를 직접 연결하지 않는다

루커 스튜디오는 **화면을 새로 그릴 때마다 쿼리를 날린다.** 필터를 한 번 바꾸면
한 번 더 날아간다. `raw` 를 연결하면 그때마다 1억 2천만 행을 읽는다 —
월 1 TiB 무료 한도는 이렇게 사라진다. **연결은 `mart` 만.**

### 그 외 주의

- **원천 필터를 반드시 건다.** 실유저는 20~50명이라 합성과 섞이면 비율이 무의미해진다.
  보고서 수준 필터로 `source = 'local'` (또는 `'supabase'`)을 고정한다
- 데이터 원본 설정에서 **캐시를 켜 둔다**(기본 켜짐). 12시간 캐시면 같은 화면을
  여러 번 봐도 쿼리는 한 번이다
- 공유는 **보고서 단위**다. 팀원은 이미 BigQuery 관리자로 붙어 있다
  ([[ops-bigquery-team-access]])
- 날짜 필드는 마트에 이미 KST 로 들어 있다. 루커에서 시간대를 또 바꾸지 않는다

## 그다음 · 데이터가 갱신되면 — 매번 도는 네 줄

만드는 것은 한 번이지만 **갱신은 계속**이다. 유저가 투표를 더 해도
그 행은 Supabase 에만 쌓인다 — 아래 네 줄이 그것을 대시보드까지 옮긴다.

```
python pipeline/extract_load.py --source supabase    # ① 새 행을 raw 로
python pipeline/verify_load.py  --source supabase    # ② 빠진 행이 없는지
python qa/quality_check.py      --source supabase    # ③ 믿어도 되는지
python bigquery/build.py --layer mart                # ④ 마트를 다시 굽는다
```

### 층마다 다시 해야 하는가

| 층 | 다시 하나 | 왜 |
|---|---|---|
| `raw` | **한다** (①②) | 여기가 유일한 입구다 |
| `stg` | **안 한다** | 뷰는 데이터를 갖고 있지 않다. ①이 끝나면 이미 최신이다. **SQL 을 고쳤을 때만** `--layer stg` |
| `mart` | **한다** (④) | 테이블은 만든 시점에 굳은 값이다. 안 돌리면 **오류 없이 옛날 숫자**가 뜬다 |
| 루커 | **안 한다** | 마트를 다시 읽는다. 다만 캐시가 기본 12시간이라 즉시 보려면 새로고침 |

### ④ 는 ① 과 성격이 다르다 — 안에서 굽는 일이다

| | `extract_load.py` | `build.py` |
|---|---|---|
| 무엇이 오가나 | **행 자체.** Postgres 에서 꺼내 올린다 | **SQL 글자만** 몇 KB. 데이터는 BigQuery 밖으로 안 나간다 |
| 어디서 계산하나 | 파이썬이 행을 만진다 | BigQuery 서버 안. 파이썬은 심부름꾼이다 |
| 하는 일 | 바뀐 행만 골라 `MERGE` | `CREATE OR REPLACE TABLE ... AS SELECT` — 통째로 갈아끼운다 |
| 비용 | 주로 시간. 파티션 한도에 걸릴 수 있다 | 읽은 스캔량 + 만들어진 표의 저장 용량 |

**갈아끼우는 동안에도 옛 표가 보인다.** 새 표가 완성된 뒤에 바뀌므로
굽는 중에 대시보드를 열어도 반쯤 만들어진 숫자가 보이지 않는다.

### ⚠️ 증분이 못 잡는 두 경우

둘 다 **오류가 안 나고 값만 빈다.** ①에서 그 표만 `--full-refresh` 로 다시 받는다.

- **컬럼을 추가했을 때** — `updated_at` 이 안 움직여 증분이 아무것도 못 잡는다
  (P5 의 "필수값" 검사가 이걸 잡는다)
- **과거 시각으로 되돌리는 백필을 돌렸을 때** — 워터마크보다 과거라 눈에 안 띈다

### 얼마나 자주

- **지금은 손으로 돈다.** 자동 갱신이 없어 돌린 만큼만 최신이다
  (2026-08-18 에 12일 멈춰 있던 것이 그래서다)
- 클로즈드 테스트 중에는 **하루 한 번**이면 충분하다. 네 줄 다 해도 스캔은
  12 GiB 남짓 — 월 무료 한도의 1.1%
- 번거로워지면 네 줄을 **Airflow DAG 하나**로 묶는다.
  `airflow/dags/ping_raw_load.py` 가 이미 ①을 하고 있다
- 마트가 커지면 그때 부분 갱신으로 바꾼다. **지금 규모에서는 통째로 다시 굽는 편이
  단순하고 틀릴 여지가 적다**

## 두 축으로 나눈다 — 탐색은 합성, 배달은 실유저

⚠️ **2026-08-18 논의에서 방향을 잡았다. 아직 결정 노드로 굳히지 않았다.**

대시보드를 어떻게 쓸 것인가에 두 갈래가 있고, **원천만 다른 게 아니라 성격이 다르다.**

| | 배달 (실유저) | 탐색 (합성) |
|---|---|---|
| 묻는 것 | **이번 주에 무슨 일이 있었나** | 이 서비스는 어떻게 생겼나 |
| 단위 | 사건과 개수 | 비율과 분포 |
| 기간 | 지난 한 주 | 12개월을 잘라 가며 |
| 성격 | 감시 — 미는 것(push) | 탐색 — 당기는 것(pull) |

### 만들 것은 셋

| | 무엇 | 어디서 |
|---|---|---|
| ① | 합성 대시보드 (기간 필터로 탐색) | 루커 · **이미 스케치가 있다** |
| ② | 같은 형태의 **실유저 사본** | 루커에서 사본 + 원천 필터만 바꾼다 |
| ③ | 주간 **표지 요약** | DAG 가 마트를 읽어 만든다 |

②는 사본이라 실제 작업은 ①과 ③뿐이다. PDF 발송은 **루커 스튜디오 내장 예약 발송**을
쓴다 — DAG 로 만들면 헤드리스 브라우저를 떠안게 되고 얻는 것이 없다.

### 표지 + 첨부 — 실제 주간 리포트의 형태

- **표지 = 텍스트 요약.** 무엇이 바뀌었나 · 처음 있는 일이 있었나 · 파이프라인은 살아 있나.
  **읽히는 부분은 여기뿐이다.**
- **첨부 = 대시보드 PDF.** 지금은 절반이 0 이지만 쌓이면 이력이 되고,
  유저가 늘면 무게중심이 저절로 이쪽으로 옮겨간다. **그때 구조를 바꾸지 않아도 된다.**

### ⚠️ 실유저 배달에 비율을 쓰지 않는다

실유저는 **23명 · 받은 투표 616건**이다(2026-08-18). 여기서 "열람률 70.5%"는
**두세 건만 움직여도 몇 %p 씩 튄다.** 매주 오르내리는 것을 보면 없는 추세를 읽게 된다.

- 절대 수로 보낸다 — `투표 47건 (지난주 12건)`
- **"처음 있는 일"을 따로 싣는다** — 첫 결제 · 첫 탈퇴 · 첫 신고 · 첫 게시글.
  20명 규모에서는 지표보다 **사건이 정보다.** 빈 표에 첫 행이 들어온 것도 여기 붙는다
- **매출 줄은 넣지 않는다.** 실유저 충전은 전부 스텁이라 매주 ₩0 이 온다.
  대신 "충전 버튼 N회"로 참여만 센다
- 대시보드에서도 비율 옆에 분모를 함께 띄운다 — `70.5% (434 / 616)`

### 섞이지 않게 만드는 장치

- 스냅샷 표의 키를 **`(as_of_date, source)`** 로 잡는다. 두 원천이 같은 표에 주별로
  나란히 쌓이고, **배달은 supabase 행만 · 탐색은 local 행만** 읽는다. 표는 하나인데 섞일 수 없다
- 덤으로 **"지난달에 이 지표가 얼마였지?"가 표에 남는다** — 대시보드는 늘 현재만 보여준다
- 화면과 메일 **양쪽에 원천을 눈에 보이게 박는다.** 같은 이름의 지표가 두 곳에서 다른 숫자로
  나오므로, 어느 쪽을 보는지 헷갈리는 순간 잘못된 결론이 나온다

### 갱신 주기가 다르다

- **실유저는 매일** 돈다 (적재 → 검증 → 품질 → 마트 → 스냅샷 → 주 1회 발송)
- **합성은 재생성했을 때만** 돌린다. 재생성 전까지 값이 안 변하므로 매일 구울 이유가 없다
- DAG 는 원천을 **파라미터로 받게** 짠다. 같은 코드로 둘 다 된다

### ⚠️ 배달에서 반드시 지킬 것 둘

- **실패도 배달한다.** 적재가 멈추거나 품질검증이 깨지면 메일이 **안 오는 게 아니라**
  "이번 주 데이터 없음 — 적재 실패"가 와야 한다. 안 오는 것과 문제가 없는 것을
  구분할 수 없으면 12일 멈춰 있어도 아무도 모른다 — **실제로 그랬다**
- **합성이 안 변해도 발송은 건너뛰지 않는다.** "변화 없음(합성 v5 · 마지막 재생성 2026-08-06)"을
  명시해 보낸다. 안 보내면 파이프라인이 죽은 것과 구분되지 않는다

⚠️ **Airflow 스케줄은 UTC 다.** 월요일 아침 9시 KST 로 받으려면 일요일 00:00 UTC 로 건다.

**아직 안 정한 것** — 받는 수단(슬랙 / 이메일).

## 자주 나는 오류

| 메시지 | 뜻 | 할 일 |
|---|---|---|
| `Dataset ... was not found` | `stg`/`mart` 데이터셋이 없다 | `build.py` 를 한 번 돌리면 만든다 |
| `Not found: Table ... stg_user` | stg 를 안 만들고 mart 를 돌렸다 | `--layer stg` 부터 |
| `403 ... quota exceeded` | 무료 한도(쿼리 1 TiB/월) | `--estimate` · `--dry-run` 으로 먼저 재는 습관 |
| 품질검사에서 "참조" 위반 | 부모 없는 자식 행 | 적재 순서 문제일 때가 많다. `--full-refresh` 로 그 표만 다시 |
| 품질검사에서 "필수값" 위반 | 컬럼을 추가했는데 증분이 못 잡았다 | 그 표를 `--full-refresh` |
