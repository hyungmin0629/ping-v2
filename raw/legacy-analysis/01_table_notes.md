# `final` DB 테이블별 메모

조사 시점: 2026-07-27 / DB: `mysql` 컨테이너(포트 3307) → `final` 스키마

## 🔑 전체를 관통하는 핵심 발견 (먼저 읽어야 할 것)

1. **극소수 파워유저 쏠림.** `accounts_pointhistory`(233만 행), `accounts_userquestionrecord`(122만 행), `polls_questionset`(15.8만 행)의 distinct `user_id`가 각각 **5,037 / 4,849 / 4,972명**뿐이다. 전체 가입자 677,085명의 **0.7%도 안 되는 인원이 투표/포인트 활동 대부분을 생성**한다. `user_id` 범위(838,023~1,583,358)와 NULL 여부를 확인했으나 컬럼 매핑 오류는 아니고 실제 쏠림이다. 활동 지표를 유저 단위로 집계할 때 이 소수 그룹이 평균을 심하게 왜곡할 수 있으니 반드시 분모를 "전체 가입자"가 아니라 "실제 활동 유저"로 나눠서 봐야 한다.
2. **탈퇴 기록에 user_id가 없다.** `accounts_userwithdraw`(70,764건, 전체 가입자의 10.5%)는 `reason`, `created_at`만 있고 어떤 유저가 탈퇴했는지 특정할 수 없다. 개인정보 익명화 처리로 추정.
3. **질문 마스터 데이터는 초기 한 번만 적재됨.** `polls_question`(5,025개)이 전부 2023-03-31~2023-06-06 사이에 생성되고 이후 추가가 없다. 반면 실제 질문 노출(`polls_questionpiece`)은 2024-05까지 계속 발생 → 같은 질문 풀을 계속 재사용하는 구조.
4. **이벤트 기능은 사실상 거의 안 쓰임.** `events` 테이블에 전체 서비스 기간 통틀어 **3개**뿐이고 전부 2023년에 종료됨(`is_expired=1`).
5. **거의 모든 활동 테이블이 2023년 5월 한 달에 몰림.** 친구요청·포인트·투표기록·usercandidate 등 대부분이 런칭 직후인 2023-05에 전체의 70~90%가 발생하고 이후 급감하는 동일한 패턴 → 전형적인 "런칭 스파이크형" 데이터.

## 8. `hackle` DB — 핵클(Hackle) 이벤트 트래킹 테이블

원래 `final`에 잘못 적재됐다가 별도 `hackle` DB로 이동한 4개 테이블. 이 DB의 `hackle_events`만 날짜 컬럼(`event_datetime`)이 있고 나머지 3개는 스냅샷/속성 테이블이라 날짜가 없음.

### 핵심 발견
1. **추적 기간이 매우 짧다.** `hackle_events`는 **2023-07-18 ~ 2023-08-10, 단 24일**뿐이다. `final` DB가 2023-03~2024-05(14개월) 전체를 담고 있는 것과 대조적 — 핵클 연동은 극히 일부 구간(파일럿 또는 특정 실험 기간)만 존재하는 것으로 보인다.
2. **`id`와 `event_id`는 완전히 같은 값(중복 컬럼).** 11,441,319건 전체에서 두 컬럼이 100% 일치 — 이벤트 고유 UUID를 두 컬럼에 중복 저장한 것으로, 조인/분석 시 하나만 쓰면 된다.
3. **user_id 스키마가 두 종류로 섞여 있다.** 숫자형 ID(= `final.accounts_user.id`, 범위 831,962~1,579,932와 일치)와 Firebase UID 문자열이 공존. `hackle_properties`는 이 비율이 **numeric 63.6% / firebase 36.4%**로 상당히 섞여 있어 `final.accounts_user`와 바로 조인되지 않는 행이 1/3 이상이다. 버전별로 보면 1.2.x(레거시)는 거의 100% firebase 방식이고, 2.0.x로 넘어온 뒤에도 약 33~38%가 여전히 firebase UID로 남아 있다 — 완전한 ID 마이그레이션이 이루어지지 않은 상태. 조인하려면 `accounts_user.firebase_uid` 보조 매핑이 필요하다. 반면 `user_properties.user_id`는 230,817/230,819(99.99%)가 numeric이라 바로 조인 가능.
4. **`session_id`/`device_id` 정합성은 양호.** `hackle_events`의 distinct `session_id`(253,616), `hackle_properties`의 distinct `session_id`(253,616) 및 distinct `device_id`(251,720), `device_properties`의 distinct `device_id`(251,720)가 서로 정확히 일치 — 조인 키로 신뢰할 수 있다.

|---|---|---|---|---|---|
| `hackle_events` | 이벤트 로그 | 11,441,319 (최대 테이블) | id/event_id 11,441,319(이벤트당 고유) · session_id 253,616 · question_id 3,897 | **2023-07-18 ~ 2023-08-10** | 상위 이벤트: view_lab_tap(126.7만) · view_timeline_tap(119.5만) · $session_start(103.7만) · launch_app(98.6만) · click_question_open(81.7만). question_id 3,897개는 `polls_question` 전체(5,025)의 77.5% |

## 후속으로 확인해볼 만한 것
- 파워유저 ~5,000명 그룹과 `accounts_user_contacts`, `accounts_userwithdraw`(비율), `accounts_paymenthistory` 간의 교차 (실제 과금/잔존과 활동 집중도의 상관관계)
- `accounts_failpaymenthistory`가 2023-09 이후 끊긴 이유(로직 변경 여부)를 코드 히스토리에서 확인
- `accounts_timelinereport` 중단 시점과 `polls_questionreport` 도입/강화 시점이 겹치는지 확인
- `hackle_properties`의 firebase-UID 36.4% 행을 `accounts_user.firebase_uid`로 매핑해서 실제 커버리지(전체 유저 대비 핵클 트래킹 비율)를 정확히 산출
- 핵클 추적 기간(2023-07-18~08-10)이 왜 이 24일로 한정되는지 확인(파일럿 종료/계약 종료/덤프 추출 범위 등) — `final`의 전체 활동 기간과 겹쳐서 봐야 정확한 비교가 됨
